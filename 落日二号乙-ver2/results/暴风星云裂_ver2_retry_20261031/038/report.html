F-1 038.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：038.php:11-13

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入，该输入在 038.php:5 被读取后未做任何类型校验、转义或参数化，直接以字符串拼接方式进入 038.php:11 构造的 SQL 语句：`SELECT first_name, last_name FROM users WHERE user_id = '$id';`。由于 `$id` 被单引号包裹但未经过 mysqli_real_escape_string 或预处理语句绑定，攻击者可闭合单引号注入任意 SQL 片段（如 `1' OR '1'='1` 或 UNION 查询）。拼接完成的 `$query` 在 038.php:13 传入 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行，构成完整的 source→sink 污点链。代码中仅移除了 `or die` 以抑制错误回显，并未引入任何净化逻辑，因此校验完全缺失。

影响：数据库查询逻辑被攻击者完全控制：可绕过 user_id 条件读取 users 表全部记录（first_name、last_name 等），并通过 UNION SELECT 进一步读取当前数据库其他表（如账号、口令散列）乃至 information_schema 元数据，造成敏感数据泄露；在数据库账号权限较高时还可结合堆叠/文件写入能力扩大影响。属于未授权远程数据泄露风险。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入点为 HTTP query 参数 `id`，任何能访问 038.php 的远程用户均可触发，无需认证；利用链闭合：038.php:5 读取输入 → 038.php:11 字符串拼接进 SQL → 038.php:13 mysqli_query 执行，中间无白名单、无转义、无参数化，攻击者可控输入直达 SQL 解析器。证据等级为源码推断（llm_inferred），未做动态验证。

修复建议：改用预处理语句与参数绑定：`$stmt = $GLOBALS["___mysqli_ston"]->prepare("SELECT first_name, last_name FROM users WHERE user_id = ?"); $stmt->bind_param("i", $id); $stmt->execute();`，并将 `$id` 强制转换为整数（`$id = (int)$_GET['id']`）作为纵深防御；若必须拼接，使用 mysqli_real_escape_string 并配合类型白名单校验；同时为数据库账号授予最小权限，关闭详细错误回显。

F-2 DVWA SQL 注入（038.php）：GET 参数 id 直接拼接进 mysqli/SQLite 查询

high sql_injection / CWE-89 · 置信度 0.88 · candidate / llm_inferred

位置：038.php:5-34

038.php 在 isset($_GET['Submit']) 时读取 $_GET['id']（第 5 行），未做任何类型转换、转义或参数化，直接以单引号包裹拼入 SQL 语句（第 11 行 MySQL 分支、第 32 行 SQLite 分支），随后分别交给 mysqli_query（第 13 行）与 $sqlite_db_connection->query（第 34 行）执行。攻击者可通过闭合单引号注入任意 SQL，读取 users 表以外的数据（如用户名口令哈希），并借助第 44-52 行的布尔回显（存在/不存在）与 404 状态差异做布尔盲注。

影响：可读取数据库任意数据（含用户口令哈希），并可作为进一步攻击的跳板；布尔盲注可在无回显情况下逐字符提取数据。

CVE/CWE 论证：CWE-89。外部 GET 参数直达 SQL 汇点，无认证要求（脚本本身无鉴权逻辑），链路在 CODE PACK 内完整闭合。

修复建议：使用预处理语句（mysqli_prepare/bind_param 或 PDO 参数绑定），并对 id 做整型强制转换（(int)$id）。
