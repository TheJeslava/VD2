F-1 042.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.85 · candidate / rule_verified+llm

位置：042.php:10-12

攻击者通过 HTTP 请求的 query 参数 `id`（042.php:5 读取）提交任意字符串。该值未经任何过滤、类型转换或参数化，被直接拼接进 SQL 语句：042.php:11 `$query = "SELECT first_name, last_name FROM users WHERE user_id = $id;"`，随后在 042.php:12 传入 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。由于 `$id` 处于数值上下文且无引号包裹，攻击者可构造如 `1 UNION SELECT user, password FROM users` 或布尔/时间盲注载荷改变查询语义。校验无效的原因：代码路径中不存在 `intval()`、`mysqli_real_escape_string()`、预处理语句或白名单校验，污点从 source 到 sink 全程未净化。

影响：数据库数据泄露：可读取 users 表之外的任意表（如用户名/口令哈希），并可进一步通过 UNION/盲注枚举数据库结构；结合 042.php:12 的 `mysqli_error` 回显，错误信息会直接输出到响应，构成报错型注入，显著降低利用门槛。若数据库账户权限过高，还可能造成数据篡改。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问 042.php 触发；利用链闭合：source（042.php:5 query `id`）→ 字符串拼接（042.php:11）→ 执行汇点（042.php:12 mysqli_query），中间无净化函数，且错误信息回显（mysqli_error）为攻击者提供反馈通道。

修复建议：改用参数化查询/预处理语句：`$stmt = $mysqli->prepare("SELECT first_name, last_name FROM users WHERE user_id = ?"); $stmt->bind_param("i", $id);`，并对 `id` 做 `intval()` 或严格数字白名单校验；关闭生产环境的 `mysqli_error` 回显，改为记录日志；数据库账户遵循最小权限，仅授予所需表的 SELECT 权限。

F-2 042.php:55 查询为常量语句，未构成可利用 SQL 注入（证据不足）

critical sql_injection / CWE-89 · 置信度 0.4 · candidate / rule_verified+llm

位置：042.php:53-55

候选声称 042.php:53-55 存在 SQL 注入，source 指向 042.php:5 的 query 参数 `id`。但代码片段显示 042.php:54 的 `$query` 被赋值为常量字符串 `"SELECT COUNT(*) FROM users;"`，042.php:55 将该常量传入 `mysqli_query` 执行。片段中不存在把外部输入 `$id` 拼接到该 `$query` 的语句，因此 source 与 sink 之间缺少数据流连接。若 042.php:5 的 `$id` 与 042.php:54 的 `$query` 之间存在片段未展示的赋值关系，则属于证据缺口，无法在现有证据下确认。

影响：证据不足：在给定代码片段范围内，042.php:55 执行的是固定常量查询，攻击者无法通过 `id` 参数影响该语句，暂不能认定数据泄露或篡改影响。

CVE/CWE 论证：CWE-89 的成立需要外部可控数据到达 SQL 执行汇点。当前证据中 042.php:54 的 `$query` 为字面量常量，042.php:55 的 `mysqli_query` 参数不包含外部输入，污点链在片段内不闭合，故不满足 CWE-89 的利用条件。

修复建议：若后续确认存在将外部输入拼入该 `$query` 的代码，应统一改为参数化查询并做类型校验；对常量查询无需改动。建议补充 042.php:5 至 042.php:54 之间的完整代码以复核数据流。
