F-1 039.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.73 · candidate / rule_verified+llm

位置：039.php:13-15

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（039.php:5 读取该参数），该值未经任何类型转换、转义或参数化，直接被拼接进 SQL 语句：039.php:13 `$query = "SELECT first_name, last_name FROM users WHERE user_id = $id;"`。由于 `$id` 位于 SQL 的数值比较位置且无引号包裹，攻击者可注入 `1 UNION SELECT ...`、`1 OR 1=1` 等片段改变查询语义。随后在 039.php:15 该拼接后的 `$query` 被传入 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行，污点从 source 到 sink 全程无有效净化，利用链闭合。代码注释显示移除了 `or die` 以抑制 MySQL 错误回显，但这只影响报错信息的可见性，不构成任何防护。

影响：数据库数据泄露：攻击者可通过 UNION 注入读取 users 表之外的任意表（如用户名、口令哈希、其他业务数据），也可通过布尔/时间盲注逐字节提取数据；在数据库账户权限较高且支持堆叠查询时可能进一步写入或篡改数据。属于未授权远程可利用的机密性/完整性破坏。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问该脚本；利用链闭合：039.php:5 读取参数 → 039.php:13 字符串拼接 → 039.php:15 `mysqli_query` 执行，中间无白名单、无 `intval`、无 `mysqli_real_escape_string`、无预处理语句。证据等级为源码推断（llm_inferred），未做动态验证。

修复建议：改用参数化查询：`$stmt = $GLOBALS["___mysqli_ston"]->prepare("SELECT first_name, last_name FROM users WHERE user_id = ?"); $stmt->bind_param("i", $id); $stmt->execute();`。若必须保留拼接，至少对 `$id` 做严格整数校验（`filter_var($id, FILTER_VALIDATE_INT)` 失败即拒绝）并配合 `mysqli_real_escape_string`；同时为数据库账户实施最小权限，关闭详细错误回显到客户端。
