F-1 042.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：042.php:10-12

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（042.php:5 读取该参数），该值未经任何过滤、类型转换或参数化，被直接拼接进 SQL 语句：042.php:11 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = $id;"`，随后在 042.php:12 通过 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。由于 `$id` 处于 WHERE 条件的数值位置且无引号包裹，攻击者可注入 `1 OR 1=1`、`1 UNION SELECT ...` 等片段改变查询语义；代码中不存在 mysqli_real_escape_string、intval、预处理语句或白名单校验，因此校验完全缺失。错误信息还会经 `mysqli_error(...)` 回显（042.php:12 的 die 分支），进一步泄露数据库结构，便于构造 UNION 注入。

影响：可读取 users 表之外的数据（如通过 UNION 提取数据库名、表名、其他表字段），造成敏感数据泄露；结合堆叠/写文件能力可能进一步导致数据篡改或服务器文件写入（取决于数据库权限）。错误回显降低了利用门槛。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问 042.php 触发；利用链闭合：source（042.php:5 的 `id`）→ 字符串拼接（042.php:11）→ 执行汇点 `mysqli_query`（042.php:12），中间无净化函数，链路完整。证据等级为源码推断（llm_inferred），未做动态验证。

修复建议：改用参数化查询：`$stmt = $GLOBALS["___mysqli_ston"]->prepare("SELECT first_name, last_name FROM users WHERE user_id = ?"); $stmt->bind_param("i", $id); $stmt->execute();`；若必须拼接，先对 `$id` 做 `intval()` 强制数值化并校验范围。关闭向用户回显的 `mysqli_error` 详细信息，改为记录到服务端日志。数据库账号遵循最小权限，禁止 FILE 权限。
