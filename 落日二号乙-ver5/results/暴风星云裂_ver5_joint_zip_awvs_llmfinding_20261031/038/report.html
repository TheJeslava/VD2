F-1 038.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：038.php:11-13

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（038.php:5 读取该参数），该值未经任何类型转换、转义或参数化即被拼接进 SQL 语句：038.php:11 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id';"`，将 `$id` 直接置于单引号字符串字面量内部；随后 038.php:13 调用 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行该拼接语句。由于 `$id` 中的单引号可闭合 `'$id'` 字面量，攻击者可注入任意 SQL 片段（如 `1' OR '1'='1`、`1' UNION SELECT ...`），校验无效的根本原因是全程无 `mysqli_real_escape_string`、无 `intval` 强转、无预处理语句绑定参数，仅靠字符串拼接。代码注释显示已移除 `or die` 以抑制 MySQL 错误回显，这降低了报错型注入的可见性，但不影响布尔/联合注入的可行性。

影响：数据库数据泄露：可读取 users 表及其他表的任意数据（如凭据、个人信息）；通过 UNION 查询可跨表提取数据；在数据库账户权限较高且支持堆叠/文件写入的情况下，可能进一步导致数据篡改或服务器文件读写，进而扩大为代码执行。属于未授权远程可达的严重数据安全风险。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素的不当中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问 038.php；利用链闭合：source（038.php:5 的 `id`）→ 字符串拼接（038.php:11）→ 执行汇点 `mysqli_query`（038.php:13），中间无有效净化，攻击者可控输入直达 SQL 解析器，满足注入成立的全部条件。

修复建议：改用预处理语句与参数绑定：`$stmt = mysqli_prepare($link, "SELECT first_name, last_name FROM users WHERE user_id = ?"); mysqli_stmt_bind_param($stmt, 'i', $id); mysqli_stmt_execute($stmt);`，并对 `id` 做 `intval()`/白名单校验；禁止将外部输入拼接进 SQL 文本；为数据库账户配置最小权限，避免 FILE 等高风险权限；生产环境关闭详细错误回显。
