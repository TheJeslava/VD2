F-1 009.php 用户存在性检查 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：009.php:20-22

攻击者通过 HTTP 请求参数 user_id 输入（009.php:17 读取 query `user_id` 到变量 $id），该值未经任何转义或参数化即被拼接进 SQL 字符串：009.php:21 `$check_query = "SELECT user_id FROM users WHERE user_id = '$id'"`，随后在 009.php:22 通过 mysqli_query($GLOBALS["___mysqli_ston"], $check_query) 执行。由于 $id 被直接放入单引号字符串字面量内，攻击者可闭合引号并注入任意 SQL 片段（如 `1' OR '1'='1` 或 UNION 查询），校验无效的原因是代码仅做了字符串拼接，未使用 mysqli_real_escape_string、预处理语句或类型强制转换（如 intval）。

影响：数据库查询逻辑被完全控制：可绕过用户存在性判断、通过 UNION 读取 users 表及其他表的任意数据（口令哈希、个人信息），并可结合堆叠/报错注入进一步获取数据库结构，造成敏感数据泄露与认证逻辑绕过。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入点为 HTTP 请求参数 user_id，属于远程可访问入口；无需认证即可触发该查询路径；利用链闭合：source（009.php:17 的 user_id）→ 拼接（009.php:21）→ 危险汇点 mysqli_query（009.php:22），中间无有效净化，攻击者输入可直接改变 SQL 语义。

修复建议：改用预处理语句与参数绑定：`$stmt = $mysqli->prepare('SELECT user_id FROM users WHERE user_id = ?'); $stmt->bind_param('i', $id); $stmt->execute();`；若必须使用字符串拼接，至少对 $id 做 intval 强制类型转换或 mysqli_real_escape_string 转义，并对 user_id 做数字白名单校验；同时为数据库账户配置最小权限。

F-2 009.php 用户信息查询 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：009.php:27-29

同一外部输入 user_id（009.php:17 读取到 $id）在通过存在性检查后，被再次拼接进第二条 SQL：009.php:28 `$query = "SELECT first_name, last_name, user_id, avatar FROM users WHERE user_id = '$id';"`，并在 009.php:29 由 mysqli_query($GLOBALS["___mysqli_ston"], $query) 执行。$id 仍处于单引号字面量内且未转义，攻击者可闭合引号注入 UNION SELECT 等语句，直接控制返回的列数据。校验无效的原因与上一条一致：无参数化、无转义、无类型约束。

影响：攻击者可读取 users 表任意列（first_name、last_name、avatar 等）乃至通过 UNION 读取其他表数据，导致用户个人信息泄露；返回结果还会被后续页面逻辑使用，可能进一步影响展示与业务判断。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入源为 HTTP 参数 user_id，远程可达；无需认证；利用链闭合：source（009.php:17）→ 拼接（009.php:28）→ 汇点 mysqli_query（009.php:29），无有效净化。

修复建议：使用预处理语句绑定参数（bind_param('i', $id)）；对 user_id 做整数强制转换与白名单校验；禁止将外部输入直接拼入 SQL；数据库账户遵循最小权限原则。

F-3 009.php 日志写入 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.63 · candidate / rule_verified+llm

位置：009.php:71-73

009.php:71-72 构造日志插入语句 `INSERT INTO bac_log (user_id, target_id, ip_address) VALUES ({$current_user_id}, {$target_id}, '{$ip}')`，其中 {$current_user_id} 与 {$target_id} 以无引号形式直接拼接，'{$ip}' 以单引号包裹但未转义，随后在 009.php:73 由 mysqli_query($GLOBALS["___mysqli_ston"], $log_query) 执行。候选标注的 source 为 query `user_id`（009.php:17），该输入经业务逻辑流转到 $current_user_id/$target_id 等变量后进入日志语句；由于这些值均未做类型转换或转义，攻击者可注入任意 SQL。校验无效的原因是拼接式构造且无参数化。

影响：攻击者可向日志表写入任意数据或通过注入改变 INSERT 语义，造成数据污染、日志伪造，并可能借助报错/堆叠注入进一步探测或篡改数据库内容。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入源为 HTTP 参数 user_id，远程可达；无需认证；利用链闭合：source（009.php:17）→ 变量流转至 $current_user_id/$target_id/$ip → 拼接（009.php:71-72）→ 汇点 mysqli_query（009.php:73）。注意：本候选置信度较低（0.63），$current_user_id/$target_id 的具体赋值位置未在给定片段中展示，变量流转细节属推断。

修复建议：使用预处理语句绑定 user_id、target_id、ip_address 三个参数；对 user_id/target_id 做整数强制转换，对 $ip 使用 mysqli_real_escape_string 或参数绑定；对 IP 来源做格式校验（如 filter_var FILTER_VALIDATE_IP）。
