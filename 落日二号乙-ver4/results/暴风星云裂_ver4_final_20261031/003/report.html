F-1 003.php 基于 REQUEST_URI 的路径处理与 API 信息暴露（CWE-200）

位置：003.php:3-4

证据仅覆盖 003.php 第 3-4 行：第 3 行 `$request_url = $_SERVER['REQUEST_URI'];` 把客户端可控的请求 URI（含路径与查询串）读入变量；第 4 行 `$stripped_url = str_replace("/vulnerabilities/api/", "", $request_url);` 仅做一次字面量字符串替换，把 `/vulnerabilities/api/` 前缀从 URI 中剥离，得到 `$stripped_url`。输入中未提供第 5 行之后的代码，因此无法确认 `$stripped_url` 最终被用于路由分发、文件包含、数据库查询还是直接回显到响应体，也无法确认是否存在鉴权判断与返回字段白名单。就现有证据而言，能确认的只是：一个对外可达的 API 入口把原始 REQUEST_URI 作为后续逻辑的输入，且处理方式为朴素字符串替换而非规范化解析。所谓“API 信息泄露”的具体泄露字段、泄露对象与触发条件在给定片段中均无直接证据，属于规则语义命中，需运行时响应对比（版本号、鉴权差异、返回字段集合）才能坐实。

影响：证据不足。若后续代码将 `$stripped_url` 直接回显或用于拼接响应/错误信息，可能向未授权访问者泄露内部路径结构、API 版本或后端路由信息（信息泄露，CWE-200）；若用于文件或路由解析，还可能延伸为路径处理类问题。但在仅有两行代码的前提下，无法确认泄露的具体数据内容与影响面，不应据此断言高危。

CVE/CWE 论证：CWE-200（Exposure of Sensitive Information to an Unauthorized Actor）。外部可达性：`$_SERVER['REQUEST_URI']` 表明该脚本由 HTTP 请求直接触发，攻击者无需认证即可构造任意 URI 路径与查询串。但利用链未闭合：缺少 `$stripped_url` 的下游使用点、鉴权分支与响应构造代码，无法证明敏感信息确实被返回给未授权方。因此当前不满足 CVE 级别的“可达 + 泄露内容明确 + 无需认证”三要素，置信度维持低位。

修复建议：1) 不要用 `str_replace` 处理 URI 前缀，改用 `parse_url()` 拆分 path/query 后再按白名单匹配路由段；2) 对 API 响应实施字段白名单，禁止把内部路径、版本号、堆栈或后端地址写入响应体；3) 在入口处统一做鉴权与授权校验，未认证请求返回统一的最小化错误响应；4) 对 `REQUEST_URI` 做长度与字符集限制，避免异常输入进入下游逻辑；5) 补充该文件第 5 行之后的代码以便复核下游汇点。
