F-1 009.php 用户查询 user_id 参数 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.68 · candidate / rule_verified+llm

位置：009.php:20-22

攻击者通过 HTTP 请求的 query 参数 `user_id`（009.php:17 读取）传入恶意字符串，该值未经任何转义或参数化即被拼接进 `$check_query = "SELECT user_id FROM users WHERE user_id = '$id'"`（009.php:21），随后在 009.php:22 通过 `mysqli_query($GLOBALS["___mysqli_ston"], $check_query)` 执行。由于 `$id` 被直接放入单引号字符串字面量中，攻击者可闭合引号并注入任意 SQL 片段（如 `1' OR '1'='1` 或 UNION 查询），校验逻辑（判断用户是否存在）因此完全失效。代码中未见 mysqli_real_escape_string、预处理语句或类型强制转换等有效净化。

影响：可读取 users 表及同库其他表的数据（用户名、口令哈希、会话令牌等），并可借助 UNION/布尔/时间盲注逐字节提取数据库内容；若数据库账户权限过高，还可能进一步读写文件或影响业务数据完整性。属于未授权即可触发的数据库数据泄露。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入点为 HTTP query 参数 `user_id`，无需认证即可访问该脚本路径；利用链闭合：source（009.php:17 的 `user_id`）→ 字符串拼接（009.php:21）→ 危险汇点 `mysqli_query`（009.php:22），中间无有效校验或参数化，攻击者可控输入直达 SQL 解析器。

修复建议：改用预处理语句：`$stmt = $mysqli->prepare('SELECT user_id FROM users WHERE user_id = ?'); $stmt->bind_param('i', $id); $stmt->execute();`，并对 `$id` 做整型强制转换（`$id = (int)$_GET['user_id'];`）。若必须动态拼接，使用 `mysqli_real_escape_string` 并配合白名单校验；同时为数据库账户实施最小权限，关闭 FILE 权限。

F-2 009.php 用户详情查询 user_id 参数 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.68 · candidate / rule_verified+llm

位置：009.php:27-29

同一外部输入 `user_id`（009.php:17）在通过存在性检查后，被再次拼接进 `$query = "SELECT first_name, last_name, user_id, avatar FROM users WHERE user_id = '$id';"`（009.php:28），并在 009.php:29 由 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。`$id` 未做转义或参数化，攻击者可用单引号闭合注入 UNION SELECT 等语句，从 users 表或其他表读取任意列数据。

影响：可直接泄露 users 表的 first_name、last_name、avatar 等字段，并通过 UNION 注入读取任意表（如凭据、令牌）数据，造成敏感信息批量泄露；结合前一处注入可扩大数据提取面。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：HTTP query 参数 `user_id` 无需认证即可提交；利用链闭合：source（009.php:17）→ 拼接（009.php:28）→ 汇点 `mysqli_query`（009.php:29），无有效净化，输入直达 SQL 解析。

修复建议：使用预处理语句绑定 `user_id` 为整型参数，例如 `$stmt = $mysqli->prepare('SELECT first_name,last_name,user_id,avatar FROM users WHERE user_id = ?'); $stmt->bind_param('i',$id);`；对输入做 `(int)` 转换与白名单校验；数据库账户最小权限。

F-3 009.php 日志写入语句 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.58 · candidate / rule_verified+llm

位置：009.php:71-73

在日志写入分支中，`$log_query = "INSERT INTO bac_log (user_id, target_id, ip_address) VALUES ({$current_user_id}, {$target_id}, '{$ip}')"`（009.php:71-72）将多个变量直接拼接进 SQL，其中 `$target_id` 与 `$ip` 等值可追溯至外部输入（`user_id` 参数及客户端可控的 IP 来源），随后在 009.php:73 由 `mysqli_query($GLOBALS["___mysqli_ston"], $log_query)` 执行。由于 `$target_id` 未加引号且未做类型约束，攻击者可注入任意 SQL 片段（如 `1); DROP/UPDATE ...` 或子查询），`$ip` 位于单引号内亦可闭合注入。

影响：可向 bac_log 表写入伪造记录、篡改或删除日志（掩盖攻击痕迹），并通过子查询/报错注入读取其他表数据；日志完整性被破坏会影响审计与溯源。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：拼接值来源于 HTTP 请求参数与客户端可控字段，无需认证；利用链闭合：source（009.php:17 的 `user_id` 及 IP 相关输入）→ 拼接（009.php:71-72）→ 汇点 `mysqli_query`（009.php:73），无参数化或转义。

修复建议：使用预处理语句绑定所有列值：`$stmt = $mysqli->prepare('INSERT INTO bac_log (user_id,target_id,ip_address) VALUES (?,?,?)'); $stmt->bind_param('iis',$current_user_id,$target_id,$ip);`；对 `$target_id`、`$current_user_id` 强制整型转换，对 `$ip` 使用 `filter_var($ip, FILTER_VALIDATE_IP)` 校验；日志表账户限制为仅 INSERT 权限。

F-4 DVWA 用户资料页通过硬编码 token 绕过访问控制，任意读取他人资料（IDOR/BAC）

high idor / CWE-639 · 置信度 0.85 · candidate / llm_inferred

位置：009.php:13-47

009.php 第 13 行从 $_GET 读取 action 与 user_id，第 14 行仅用 /^\d+$/ 校验 user_id 为纯数字，第 26 行用 `$_GET['token'] == 'user_token'` 作为唯一“授权”判断，该 token 为硬编码常量且源码注释（第 39、46 行）直接泄露。攻击者只要带上 token=user_token 并遍历 user_id，即可在第 28-29 行查询并回显任意用户的 first_name/last_name/avatar，完全绕过“当前用户”身份校验（第 7 行查出的 $current_user_id 从未用于比对）。

影响：任意用户可读取全部用户资料，越权访问敏感个人信息

CVE/CWE 论证：CWE-639 授权绕过/IDOR；外部 GET 可达，token 硬编码于源码，链闭合

修复建议：移除硬编码 token，改为服务端会话身份与目标 user_id 归属校验
