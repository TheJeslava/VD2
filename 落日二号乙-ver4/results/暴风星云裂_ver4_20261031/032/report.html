F-1 客户端令牌生成使用 MD5 弱哈希（CWE-328）

medium weak_crypto / CWE-327 · 置信度 0.6 · candidate / rule_verified+llm

位置：032.php:17-18

在 032.php 第 17-18 行，页面脚本从 DOM 元素 phrase 读取用户输入（document.getElementById("phrase").value），先经 rot13 做可逆替换，再调用 md5() 生成令牌并写入 document.getElementById("token").value。该令牌完全在浏览器端计算，算法为 MD5（128 位、已被证明存在碰撞且不适合安全用途），前置变换 rot13 只是字符置换、不引入任何密钥或随机性，因此令牌对相同 phrase 恒定可预测。此处不存在服务端校验环节的证据，校验有效性无法确认，但算法选择本身即构成弱哈希实现弱点。

影响：若该 token 被用作会话标识、表单防伪令牌或完整性校验值，攻击者可离线枚举/碰撞构造合法 token，导致令牌伪造、请求伪造或校验绕过；由于 rot13 可逆且无密钥，任何获得算法与输入格式的人都能复现同一 token。当前证据仅覆盖客户端生成逻辑，服务端如何使用该 token 证据不足。

CVE/CWE 论证：CWE-328（Use of Weak Hash）：MD5 用于生成安全相关令牌，抗碰撞性与抗原像性均不满足安全要求；触发点位于 032.php:18 的 md5(rot13(phrase)) 调用，属实现型弱点，无需认证即可在客户端复现算法，利用链为「用户输入 phrase → rot13 可逆变换 → MD5 → token 字段」，闭合性依赖服务端是否信任该 token（证据不足）。

修复建议：1) 令牌应由服务端使用 CSPRNG（如 Java SecureRandom、PHP random_bytes、Node crypto.randomBytes）生成，禁止在客户端计算安全令牌；2) 若必须做摘要，改用 SHA-256 及以上并配合服务端密钥的 HMAC；3) 令牌需具备足够熵（≥128 位）、一次性使用与有效期；4) 移除 rot13 这类可逆混淆，避免造成「已加密」的错觉。
