F-1 019.php 未校验的 include 参数导致路径穿越/任意文件包含（CWE-22）

high path_traversal / CWE-22 · 置信度 0.4 · candidate / rule_verified+llm

位置：019.php:6-8

攻击者通过 POST 参数 include 提交外部输入（019.php:8 的 isset($_POST['include']) 仅判断存在性，未做任何过滤）。该值在 019.php:10 被直接拼接进 $page['body'] 的字符串中（" . $_POST['include'] . "），随后作为页面 body 内容输出/渲染。代码中不存在白名单、basename()、realpath()、路径规范化或 ../ 过滤，因此校验完全无效。注意：本候选的 source 标注为 query `include`，但源码实际读取的是 $_POST['include']，注入点为 POST 参数 include，而非 URL query。

影响：攻击者可控制页面 body 中拼接的内容，若该 body 后续被 include/require 或写入文件，则可导致任意本地文件读取/包含乃至代码执行；即使仅回显，也可注入任意 HTML/脚本内容，造成内容伪造与客户端脚本执行。具体最终危险操作取决于 $page['body'] 的消费方，该消费方不在 code_pack 中，证据不足。

CVE/CWE 论证：CWE-22 路径穿越：外部可控输入（POST include）未经规范化直接进入文件/路径相关拼接点，外部 HTTP 可达、无需认证。但利用链闭合性存疑——拼接结果进入 $page['body'] 字符串而非直接的 include()/file_get_contents() 调用，最终文件操作汇点未在 code_pack 中出现，故不能断言完整 RCE/任意文件读取链。

修复建议：1) 不要将用户输入直接拼接进路径或页面内容；2) 若确需按名加载页面，使用固定白名单映射（如 ['home','about'] => 文件路径），拒绝一切未命中项；3) 对路径使用 basename() 并配合 realpath() 校验结果仍位于允许目录内；4) 输出到 HTML 时进行 HTML 实体编码，避免内容注入。

F-3 019.php CSP 仅限制 script-src 'self' 的配置缺陷（CWE-693）

medium csp / CWE-693 · 置信度 0.4 · candidate / rule_verified+llm

位置：019.php:1-2

019.php:2 设置 $headerCSP = "Content-Security-Policy: script-src 'self';";。该策略仅限制脚本来源为同源，未设置 default-src、object-src 'none'、base-uri、frame-ancestors 等，且未禁止内联事件处理器之外的其它向量（如通过同源上传/JSONP 加载脚本）。结合 019.php:10 可将外部输入拼入 body，若攻击者能注入同源脚本引用或利用同源资源，CSP 无法有效阻断。

影响：CSP 保护不完整，降低了对 XSS/内容注入的纵深防御能力；在存在 body 注入（GEN-12e64feced48）时可被绕过，导致脚本在同源上下文执行。

CVE/CWE 论证：CWE-693 保护机制失效：策略配置过宽/不完整。属配置型弱点，无直接污点链要求，但需结合 019.php:10 的注入点评估实际可利用性；最终响应头是否真正下发需运行时确认，证据不足。

修复建议：采用严格 CSP：default-src 'none'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'；避免同源下可上传可执行脚本；配合 nonce/hash 机制。
