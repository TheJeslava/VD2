028.php:4 从 HTTP 查询参数 `page` 读取外部输入并赋给变量 `$file`，随后在 028.php:7 使用 `fnmatch("file*", $file)` 与 `$file != "include.php"` 作为唯一的准入校验。该校验基于文件名模式匹配而非路径规范化：`fnmatch` 只匹配字符串形态，不解析 `../`、绝对路径、URL 编码或空字节等路径语义，因此攻击者可通过 `page` 传入形如 `file/../../etc/passwd`、`file/../../../../var/www/config.php` 等以 `file` 开头但包含目录回溯序列的值，既满足 `fnmatch("file*")` 前缀条件，又使后续文件操作解析到预期目录之外。校验未使用 `realpath()`/`basename()` 做规范化，也未将结果限制在固定白名单目录内，属于典型的黑名单/模式匹配式路径校验失效。

影响：攻击者可读取 Web 进程权限可访问的任意文件（配置文件、数据库凭据、源码、/etc/passwd 等），造成敏感信息泄露；若该 `$file` 后续被用于 include/require 或文件写入，则可进一步升级为本地文件包含导致 RCE 或任意文件写入/覆盖。具体危险操作位于 028.php:7 之后的文件处理逻辑，输入片段未给出该行之后的代码，故最终汇点函数名证据不足。

CVE/CWE 论证：CWE-22（Improper Limitation of a Pathname to a Restricted Directory，路径穿越）。外部可达性：入口为 HTTP query 参数 `page`（028.php:4），无需认证即可触达；利用链闭合：`page` → `$file` → `fnmatch("file*")` 模式校验（可被 `file/../..` 形式绕过）→ 文件路径汇点（028.php:7 及其后续文件操作）。校验仅做字符串前缀匹配，未做规范化与目录约束，因此不构成有效防护。

修复建议：1) 不要用 `fnmatch`/字符串比较做路径安全校验；2) 使用 `realpath()` 规范化后与允许的基目录做前缀比较（`str_starts_with(realpath($path), realpath($baseDir) .
