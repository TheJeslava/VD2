F-1 055.php 留言板 INSERT 语句 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：055.php:17-19

攻击者通过 HTTP 请求向 055.php 提交留言内容（源码中对应 query 参数 `mtxMessage`，即留言 message 字段），该输入在 055.php:5 被读入后未做任何转义或参数化，直接以字符串拼接方式进入 055.php:18 构造的 INSERT 语句：$query = "INSERT INTO guestbook ( comment, name ) VALUES ( '$message', '$name' );";，其中 $message 被单引号包裹但未经过 mysqli_real_escape_string 等转义，攻击者只需在留言中提交单引号即可闭合字符串字面量并注入任意 SQL 片段（如通过 comment 字段注入子查询或堆叠语句）。随后在 055.php:19 该 $query 被直接交给 mysqli_query($GLOBALS["___mysqli_ston"], $query) 执行，构成完整的 source→sink 污点链。校验无效的原因：代码路径中不存在预处理语句（prepare/bind_param）、不存在白名单过滤、也不存在对单引号/反斜杠的转义，因此单引号闭合即可绕过。

影响：数据库写入型 SQL 注入：攻击者可篡改 guestbook 表内容、向其他表写入任意数据，并可通过报错回显（055.php:19 的 die() 分支会输出 mysqli_error）实施基于报错的库名/表名/列名枚举，进而读取数据库中的敏感数据；若数据库账号权限过高，还可能造成数据删除或越权访问。属于数据完整性与机密性双重影响。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：055.php 为 Web 可直接访问的留言提交端点，攻击者通过普通 HTTP 请求即可触达，无需认证；利用链闭合：055.php:5 读取外部输入 → 055.php:18 字符串拼接构造 SQL → 055.php:19 mysqli_query 执行，且 055.php:19 的 die() 分支回显数据库错误，为注入结果提供反馈通道。

修复建议：1) 改用参数化查询：$stmt = $GLOBALS["___mysqli_ston"]->prepare("INSERT INTO guestbook (comment, name) VALUES (?, ?)"); $stmt->bind_param('ss', $message, $name); $stmt->execute();；2) 若必须保留拼接，至少对 $message、$name 使用 mysqli_real_escape_string 转义；3) 关闭生产环境的数据库错误回显，将 mysqli_error 写入服务端日志而非返回给客户端；4) 数据库账号遵循最小权限，仅授予 guestbook 表的 INSERT 权限。
