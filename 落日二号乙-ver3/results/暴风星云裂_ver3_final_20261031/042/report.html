F-1 042.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：042.php:10-12

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（042.php:5 读取该参数），该值未经任何类型校验、转义或参数化，被直接拼接进 SQL 语句：042.php:11 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = $id;"`，随后在 042.php:12 传入 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。由于 `$id` 处于 SQL 语句的数值上下文且无引号包裹，攻击者可注入 `1 OR 1=1`、`1 UNION SELECT ...` 等片段改变查询语义；同时 042.php:12 的 `or die('<pre>' . mysqli_error(...) . '</pre>')` 会把数据库错误信息回显到响应中，为报错型注入和结构探测提供便利。校验无效的原因：代码路径中不存在 `intval()`、`mysqli_real_escape_string()`、预处理语句或白名单，污点从 source 到 sink 全程未净化。

影响：数据库数据泄露：可 UNION 查询拖取 users 表及其他表（如用户名、口令哈希）内容；可绕过 `user_id` 条件枚举全部记录；结合错误回显可推断库名、表名、列结构。若数据库账户权限过高，还可能读写文件或进一步影响数据库服务，属于高危数据泄露与完整性破坏。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问 042.php 触发；利用链闭合：042.php:5 读取 `id` → 042.php:11 字符串拼接进 `$query` → 042.php:12 `mysqli_query` 执行，且 042.php:12 的错误回显进一步降低利用门槛。证据等级为源码推断（llm_inferred），未做动态验证。

修复建议：改用预处理语句与参数绑定：`$stmt = $mysqli->prepare('SELECT first_name, last_name FROM users WHERE user_id = ?'); $stmt->bind_param('i', $id); $stmt->execute();`；若必须拼接，先对 `$id` 做严格整数校验（如 `filter_var($id, FILTER_VALIDATE_INT)` 或 `intval()`）并拒绝非法值；关闭向客户端回显数据库错误（记录到服务端日志，返回通用错误页）；数据库账户遵循最小权限，禁用 FILE 权限。
