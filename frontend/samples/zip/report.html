F-1 OrderController SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.88 · candidate / static_closed

位置：OrderController.java:8-10

外部输入来自 query `name`；攻击者可控数据经过 0 个传播/校验节点后，到达 `OrderController.java:10` 的危险操作。链路上的关键跳转与绕过原因已记录在 exploit_chain 中，未发现有效白名单、参数化或上下文编码阻断。

影响：攻击者可读取/篡改数据库、绕过认证，造成数据泄露。

CVE/CWE 论证：符合 CWE-89（SQL 注入）。漏洞位于可交付源码 OrderController.java:10，入口为 POST /orders/create，外部输入来自 query，source→sink 链已静态闭合，且未发现有效净化；具备远程触发条件。

修复建议：使用 PreparedStatement/参数化查询；禁止字符串拼接 SQL；对动态表名/列名使用白名单。

F-2 OrderController 二次注入（CWE-89）

critical second_order_injection / CWE-89 · 置信度 0.88 · candidate / static_closed

位置：OrderController.java:10-15

攻击者输入先通过 /orders/create 写入 sql（sql:orders），之后由 /orders/search 读出到变量，并在 OrderController.java:15 拼接进危险汇点。第一阶段的净化无法覆盖第二阶段的上下文，构成跨请求二次注入。

影响：攻击者可绕过第一阶段净化，在第二阶段改变 SQL/命令/模板语义，造成数据泄露、越权或 RCE。

CVE/CWE 论证：符合 CWE-89。具备外部可达写点、跨请求持久化、读取后进入危险汇点三个要素；第一阶段的输入校验不能保护第二阶段的上下文。

修复建议：对从存储读出的数据按当前上下文重新参数化/编码；不要假设写入时的转义在读取上下文仍然有效；SQL 使用参数化查询，命令使用参数数组，模板使用变量绑定。

利用链

#位置描述数据状态绕过原因
1OrderController.java:10请求 A 的 query `name` 被写入 sql（sql:orders）污点被持久化，跨请求仍存在存储层不区分代码/数据，写入成功不代表安全
2OrderController.java:14请求 B 从 sql（sql:orders）读出到变量 stored持久化数据被重新加载为程序变量读取路径通常不再做输入校验
3OrderController.java:15读出的 stored 被拼接进危险汇点：return jdbc.queryForList("SELECT * FROM orders WHERE name='" + stored + "'");二次污点进入 sink第一阶段净化与第二阶段上下文不匹配；未参数化/未白名单

POC

两阶段二次注入：第一阶段把带标记的注入载荷写入持久化存储；第二阶段触发读取已存储值并拼接进危险汇点。

  1. 写入载荷到 sql（sql:orders）
    curl -sS -X POST 'http://TARGET:8080/orders/create' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'name=x%27%20OR%20%271%27%3D%271%27%20--%20SUNSET2O'
    预期：写入成功（2xx/3xx），无参数化拒绝
  2. 触发读取已存储值
    curl -sS -X GET 'http://TARGET:8080/orders/search'
    预期：响应出现 SUNSET2O 标记、SQL 报错、全量数据或异常行为
  3. 确认持久化值在第二阶段进入 sink
    （静态证据）见 exploit_chain 的 store→read→sink 三步
    预期：无需动态验证；以响应差异/错误作为人工复核依据
