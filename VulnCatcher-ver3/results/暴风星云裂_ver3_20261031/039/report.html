F-1 039.php 中基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：039.php:13-15

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（039.php:5 读取该参数），该值未经任何类型转换、转义或参数化，被直接拼接进 SQL 语句：039.php:13 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = $id;"`，随后在 039.php:15 通过 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。由于 `$id` 处于 SQL 语句的数值上下文且无引号包裹，攻击者可注入 `1 OR 1=1`、`1 UNION SELECT ...` 等片段改变查询语义。代码中未见 mysqli_real_escape_string、intval 强制转换、预处理语句或白名单校验，因此校验完全缺失。

影响：数据库查询逻辑可被任意篡改：可绕过 user_id 条件读取 users 表全部记录（first_name、last_name），并通过 UNION 注入读取其他表（如用户名/口令散列），造成敏感数据泄露；在数据库账户权限较高时还可结合堆叠/文件写入能力扩大影响。属于未授权即可触发的数据泄露类漏洞。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问该脚本；利用链闭合：039.php:5 读取参数 → 039.php:13 字符串拼接 → 039.php:15 mysqli_query 执行，中间无净化函数，攻击者输入直达 SQL 解析器。证据等级为源码推断（llm_inferred），未做动态验证。

修复建议：改用预处理语句与参数绑定：`$stmt = $mysqli->prepare('SELECT first_name, last_name FROM users WHERE user_id = ?'); $stmt->bind_param('i', $id); $stmt->execute();`；若必须动态拼接，先对 `$id` 做 `intval()`/严格数字白名单校验，并使用 `mysqli_real_escape_string` 作为纵深防御；同时为数据库账户配置最小权限，关闭详细错误回显。
