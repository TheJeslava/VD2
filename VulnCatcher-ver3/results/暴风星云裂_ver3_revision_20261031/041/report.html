F-1 041.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：041.php:9-11

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（041.php:5 读取该参数），该值未经任何转义或类型校验，被直接拼接进 SQL 语句：041.php:10 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id';"`，随后在 041.php:11 通过 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。由于 `$id` 被包裹在单引号内且未使用 `mysqli_real_escape_string` 或预处理语句，攻击者可闭合单引号注入任意 SQL 片段（如 `1' OR '1'='1` 或 UNION 查询）。代码中不存在白名单、类型转换或参数化，校验完全缺失，因此注入必然生效。

影响：可读取数据库中任意表数据（如 users 表全部记录、其他业务表），通过 UNION/布尔/报错注入实现数据泄露；结合数据库权限可能进一步读写文件或造成数据篡改，属于高危数据泄露与数据库失陷风险。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问 041.php；利用链闭合：source（041.php:5 的 `id`）→ 字符串拼接（041.php:10）→ 执行汇点 `mysqli_query`（041.php:11），中间无有效净化，攻击者可直接控制 SQL 语义。

修复建议：改用参数化查询：使用 `mysqli_prepare` 配合 `bind_param('i', $id)` 或 PDO 预处理语句，将 `id` 作为绑定参数而非拼接；同时对 `id` 做整型强制转换（如 `(int)$id`）并校验取值范围；关闭详细数据库错误回显（当前 `die(mysqli_error(...))` 会泄露报错信息，便于报错注入），改为记录日志并返回通用错误；数据库账户遵循最小权限原则。
