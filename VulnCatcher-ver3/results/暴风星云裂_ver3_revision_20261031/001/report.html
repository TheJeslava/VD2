证据来自 001.php 第 6-7 行：页面正文直接输出一个指向 `openapi.yml` 的 HTML 链接，并附带提示语，引导访问者查看 health 相关函数并寻找漏洞。攻击者无需任何输入或认证，只需请求该页面（如 GET /001.php），即可从响应 HTML 中获知 OpenAPI 描述文件的位置；随后直接请求该静态文件即可获取全部 API 端点、参数结构、鉴权方式与内部函数命名。此处不存在参数校验环节，因为泄露并非由用户输入触发，而是页面硬编码输出所致，属于设计层面的信息暴露而非污点链漏洞。需要说明：输入证据仅包含 001.php 第 6-7 行片段，未提供 openapi.yml 的实际内容，因此“文档中是否包含敏感端点/内部字段”属于推断，证据不足。

影响：信息泄露：未认证的远程访问者可枚举 API 攻击面（端点路径、HTTP 方法、参数名与类型、鉴权要求、health/调试类函数），显著降低后续针对 health 函数的漏洞挖掘成本，可能进一步导致未授权功能调用或敏感数据读取；具体敏感字段因缺少 openapi.yml 内容而证据不足。

CVE/CWE 论证：CWE-200（Exposure of Sensitive Information to an Unauthorized Actor）。外部可达性：001.php 为可直接请求的 Web 页面，无需认证；利用链闭合：请求页面 → 响应 HTML 含 `openapi.yml` 链接 → 请求该文件获取 API 描述。但该问题本质是部署/设计层面的文档暴露，通常不单独分配 CVE，且是否构成实质敏感信息泄露取决于 openapi.yml 内容（证据不足），故不宜按 CVE 级漏洞定级。

修复建议：1) 生产环境不部署 openapi.yml 等 API 描述文件，或将其置于需认证的路径下；2) 若必须提供文档，使用独立文档站点并加访问控制（HTTP Basic/SSO）与 IP 白名单；3) 从面向公网的页面中移除指向内部文档与 health 函数的提示性文案；4) 对 health/调试类端点实施鉴权或仅绑定内网回环地址；5) 在网关层对 `*.yml`、`*.yaml`、`/openapi*` 路径返回 404。
