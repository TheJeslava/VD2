F-1 009.php 用户存在性检查 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.73 · candidate / rule_verified+llm

位置：009.php:20-22

攻击者通过 HTTP 查询参数 user_id 提供输入，在 009.php:17 被读取并赋给 $id。该值未经任何转义或参数化，直接在 009.php:21 被拼接进双引号 SQL 字符串 "SELECT user_id FROM users WHERE user_id = '$id'"，随后在 009.php:22 通过 mysqli_query($GLOBALS["___mysqli_ston"], $check_query) 执行。由于 $id 被单引号包裹且未使用 mysqli_real_escape_string 或预处理语句，攻击者可闭合单引号注入任意 SQL 片段（如 user_id=1' OR '1'='1 或 UNION 查询）。校验无效的原因：代码仅做字符串拼接，没有任何白名单、类型转换（如 intval）或参数绑定。

影响：数据库数据泄露：攻击者可读取 users 表及其他表内容（凭据、个人信息）；结合 UNION 可跨表读取；在具备 FILE 权限时可读写服务器文件，进一步可能导致 RCE。该查询位于用户存在性检查路径，属于无需认证即可触达的入口。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素的不当中和）。外部可达性：user_id 来自 HTTP 查询参数，无需认证即可访问 009.php；利用链闭合：source（009.php:17）→ 字符串拼接（009.php:21）→ mysqli_query 执行（009.php:22），全程无有效净化。

修复建议：改用预处理语句与参数绑定：$stmt = $mysqli->prepare("SELECT user_id FROM users WHERE user_id = ?"); $stmt->bind_param('i', $id); 并对 $id 做 intval 类型强制；禁止将外部输入直接拼接进 SQL。

F-2 009.php 用户详情查询 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.73 · candidate / rule_verified+llm

位置：009.php:27-29

同一外部输入 user_id 在 009.php:17 被读取为 $id，在用户存在性判断通过后（009.php:27），于 009.php:28 被拼接进 "SELECT first_name, last_name, user_id, avatar FROM users WHERE user_id = '$id';"，并在 009.php:29 由 mysqli_query 执行。$id 未做转义或参数化，单引号可被闭合注入。校验无效原因：仅字符串拼接，无预处理、无转义、无类型约束。

影响：数据泄露：攻击者可读取 users 表的 first_name、last_name、user_id、avatar 等字段，并通过 UNION 注入读取任意表数据；若数据库账户权限过高，可进一步读写文件。无需认证即可触达。

修复建议：使用预处理语句绑定 user_id 参数，并对输入做整数校验；避免字符串拼接构造 SQL。

F-3 009.php 日志写入 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.55 · candidate / rule_verified+llm

位置：009.php:71-73

在 009.php:71-72 构造 INSERT INTO bac_log (user_id, target_id, ip_address) VALUES ({$current_user_id}, {$target_id}, '{$ip}')，其中 {$ip} 被单引号包裹但未转义，{$current_user_id} 与 {$target_id} 为无引号数值位。候选标注 source 为 query user_id（009.php:17），但代码片段显示该 INSERT 直接拼接的是 $current_user_id、$target_id、$ip 三个变量，其具体来源在给定片段中未完整展示（证据不足，无法确认 user_id 是否直接流入这些变量）。可确认的是：$ip 等变量在 009.php:72 被直接拼接，009.php:73 通过 mysqli_query 执行，若其中任一变量可由外部控制（如 X-Forwarded-For 头或参数），即可注入。

影响：若 $ip/$target_id/$current_user_id 可被外部控制，攻击者可注入任意 SQL，篡改或读取 bac_log 及关联表数据，甚至通过堆叠/子查询影响其他表；日志表污染还可用于二次注入。

CVE/CWE 论证：CWE-89。外部可达性：取决于 $ip 等变量来源，代码片段未展示其赋值，故外部可达性证据不足；利用链在 009.php:72→73 处闭合（拼接→执行），但 source 端证据不足。

修复建议：对 INSERT 使用预处理语句绑定 user_id、target_id、ip_address 三个参数；对 IP 使用 filter_var($ip, FILTER_VALIDATE_IP) 校验；对数值字段做 intval 强制。

F-4 009.php 硬编码 token=user_token 访问控制可被任意用户绕过

medium auth_bypass / CWE-287 · 置信度 0.8 · candidate / llm_inferred

位置：009.php:26-28

第 26 行以 `$_GET['token'] == 'user_token'` 作为访问控制，token 为硬编码常量且注释直接提示（第 39、46 行），任何攻击者只要附加 token=user_token 即可通过校验，读取任意 user_id 的资料，构成水平/垂直越权与认证绕过。

影响：任意访问者可读取其他用户资料，绕过本应存在的访问控制。

CVE/CWE 论证：CWE-284/CWE-798 硬编码凭据导致访问控制绕过，外部可达且无需真实认证。

修复建议：移除硬编码 token，改用服务端会话与基于对象归属的授权校验。
