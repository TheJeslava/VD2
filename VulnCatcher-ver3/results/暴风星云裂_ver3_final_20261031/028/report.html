位置：028.php:5-7

028.php:4 从 query 参数 `page` 读取外部输入并赋给 `$file`，028.php:7 仅用 `fnmatch("file*", $file)` 与 `$file != "include.php"` 做白名单式校验。该校验存在两处缺陷：其一，`fnmatch` 的 `file*` 模式只约束字符串前缀，攻击者可用 `file/../../etc/passwd` 之类以 `file` 开头但含 `../` 的路径同时满足 `fnmatch` 与 `!= "include.php"`；其二，校验通过后代码未对 `$file` 做 `realpath()` 规范化、未限制基目录、未剥离 `..` 与绝对路径，随后直接将该值用于文件包含/读取（028.php:5-7 之后的包含语句）。因此攻击者可控的 `page` 值经 `$file` 直达文件操作汇点，校验形同虚设。

影响：攻击者可读取服务器任意可读文件（如 /etc/passwd、应用配置、密钥文件），造成敏感数据泄露；若目标为 PHP 文件包含，还可包含上传的恶意文件或日志文件，进而导致远程代码执行（RCE），完全控制 Web 应用进程。

CVE/CWE 论证：CWE-22（路径穿越）。外部可达性：入口为 HTTP query 参数 `page`，无需认证即可访问 028.php；利用链闭合：`page` → `$file`（028.php:4）→ 前缀校验可被 `file/../..` 绕过（028.php:7）→ 文件包含/读取汇点。校验仅做前缀匹配与单值比较，未做规范化与目录约束，故不构成有效防护。

修复建议：1) 不要直接使用用户输入拼接文件路径，改用固定枚举映射（如 `$allowed = ['home'=>'pages/home.php', ...]`），按 key 取白名单值；2) 若必须使用路径，先 `$real = realpath($base . '/' . $file)`，再校验 `str_starts_with($real, realpath($base) . DIRECTORY_SEPARATOR)`，拒绝含 `..`、绝对路径、空字节的输入；3) 关闭 `allow_url_include`，包含操作使用最小权限账户运行；4) 对非法输入返回 400 并记录审计日志。
