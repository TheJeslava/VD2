F-1 041.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：041.php:9-11

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（041.php:5 读取该参数），该值未经任何过滤、转义或类型转换，被直接拼接进 SQL 语句：041.php:10 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id';"`，随后在 041.php:11 通过 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。由于 `$id` 被包裹在单引号字符串字面量中且未调用 `mysqli_real_escape_string` 或使用预处理语句，攻击者可闭合单引号注入任意 SQL 片段（如 `1' OR '1'='1` 或 UNION 查询）。代码中不存在白名单、类型校验或参数化，校验完全缺失，因此注入必然生效。

影响：可读取 users 表全部记录（first_name、last_name），并通过 UNION 注入进一步读取数据库名、表结构及其他表数据，造成敏感数据泄露；结合 041.php:11 的 `or die(... mysqli_error ...)` 错误回显，攻击者可获得数据库报错信息用于盲注/报错注入辅助，属于未授权远程数据泄露。

CVE/CWE 论证：CWE-89（SQL 注入）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问；利用链闭合：041.php:5 读取参数 → 041.php:10 字符串拼接 → 041.php:11 `mysqli_query` 执行，全程无净化，攻击者输入直达数据库解析器。证据等级为基于源码的推断（llm_inferred），未做动态验证。

修复建议：改用参数化查询：`$stmt = $GLOBALS["___mysqli_ston"]->prepare("SELECT first_name, last_name FROM users WHERE user_id = ?"); $stmt->bind_param('s', $id); $stmt->execute();`；若必须拼接，先对 `$id` 做严格类型校验（如 `(int)$id` 或白名单数字校验）并使用 `mysqli_real_escape_string`；同时关闭生产环境的数据库错误回显（移除 041.php:11 的 `or die(mysqli_error(...))`），改为记录日志并返回通用错误。
