F-1 024.php 密码修改功能 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.4 · candidate / rule_verified+llm

位置：024.php:17-19

攻击者通过修改密码表单提交新口令，该值在 024.php:8 被读取为 `password_conf`（源码片段中对应变量 `$pass_new`），随后在 024.php:18 被直接字符串拼接进 UPDATE 语句：`$insert = "UPDATE `users` SET password = '$pass_new' WHERE user = '" . $current_user . "';"`，未做任何转义或参数化。024.php:19 通过 `mysqli_query($GLOBALS["___mysqli_ston"], $insert)` 执行该拼接语句，构成 source→sink 闭合链。由于 `$pass_new` 位于单引号字符串字面量内，攻击者提交含单引号的值即可闭合字面量并注入任意 SQL 片段（如 `' , user='admin' -- `），从而改写任意用户口令。`$current_user` 来自 `dvwaCurrentUser()`（024.php:17），属于会话派生值，不是本次注入主通道。

影响：数据库写入越权：攻击者可利用注入改写 `users` 表中任意账户（含 admin）的 password 字段，实现账户接管/提权；同时 024.php:19 的 `or die(... mysqli_error ...)` 会把数据库错误信息回显到页面，造成数据库结构与版本信息泄露，为进一步利用提供条件。

CVE/CWE 论证：CWE-89（SQL 注入）：外部可控输入 `$pass_new` 未经参数化直接拼入 SQL 并在 024.php:19 执行；该功能为 Web 表单入口，无需认证即可到达注入点（若部署未强制登录），利用链 source→sink 完整闭合，属于典型的二阶写入型注入（存储写点 024.php:18/19，读取点为后续登录校验），可导致数据篡改与账户接管。

修复建议：改用预处理语句与参数绑定：`$stmt = $mysqli->prepare("UPDATE users SET password = ? WHERE user = ?"); $stmt->bind_param('ss', $pass_new, $current_user); $stmt->execute();`；对 `$current_user` 同样使用绑定参数而非拼接；关闭 `mysqli_error` 的页面回显，改为记录服务端日志；对密码字段做长度与字符白名单校验，并在修改前校验旧口令与 CSRF token。

F-2 DVWA 密码修改接口仅依赖可伪造的 HTTP_REFERER 做来源校验，导致 CSRF 强制改密/账户接管

high business_logic / CWE-840 · 置信度 0.87 · candidate / llm_inferred

位置：024.php:3-19

024.php 第 3 行在存在 GET 参数 Change 时进入改密流程；第 5 行用 stripos($_SERVER['HTTP_REFERER'], $_SERVER['SERVER_NAME']) !== false 判断请求来源，但 HTTP_REFERER 完全由客户端控制，攻击者只要在 Referer 中放入目标站点域名（如 TARGET 或 TARGET 的子串）即可通过校验。随后第 7-8 行直接读取 password_new/password_conf，第 11 行仅比较两次输入是否相等，第 14 行 md5 后在第 18-19 行拼入 UPDATE 语句修改当前用户密码。整个流程没有任何 CSRF token、没有旧密码校验、没有 Origin/Sec-Fetch-Site 校验，攻击者可诱导已登录受害者访问恶意页面，从而把受害者密码改为攻击者已知值，实现账户接管。

影响：攻击者可在受害者不知情下修改其密码，实现账户接管；若受害者是管理员则进一步控制整个应用。

CVE/CWE 论证：CWE-352（CSRF）/CWE-290（依赖可伪造来源做认证）。外部可达，无需认证即可构造请求，仅依赖受害者已登录状态；来源校验使用可伪造的 Referer，链完整闭合。

修复建议：引入 CSRF token 并在服务端校验；改密要求验证旧密码；使用 Origin/Sec-Fetch-Site 等不可伪造信号辅助判断，不要依赖 Referer。
