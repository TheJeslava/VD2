F-1 012.php 登录查询 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：012.php:13-15

攻击者通过 HTTP 请求向 012.php 提交登录参数，源码在 012.php:5 处从 query 参数 `username`（以及同表单的密码参数）读取外部输入，未做任何转义或类型校验。该值被直接拼接进 012.php:14 的 SQL 语句：$query = "SELECT * FROM `users` WHERE user = '$user' AND password = '$pass';";，随后在 012.php:15 交由 mysqli_query($GLOBALS["___mysqli_ston"], $query) 执行。由于 $user/$pass 处于单引号字符串字面量内部且无 mysqli_real_escape_string、无预处理语句、无白名单校验，攻击者可用单引号闭合字符串并注入任意 SQL 片段（如 ' OR '1'='1 绕过认证，或 UNION SELECT 读取其他表）。此外 012.php:15 的 die() 分支会把 mysqli_error() 的原始错误信息回显到页面，构成报错型注入的辅助信息泄露通道，进一步降低盲注成本。

影响：认证绕过：构造 user=' OR '1'='1' -- 之类的载荷可使 WHERE 条件恒真，以任意/首个用户身份登录。数据泄露：通过 UNION SELECT 或布尔/报错注入读取 users 表及其他库表内容（口令哈希、个人信息）。若数据库账号权限过高，还可进一步读写文件或篡改数据。错误信息回显（mysqli_error）额外泄露库名、表名、列名等结构信息。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：012.php 为可直接 HTTP 访问的登录入口，参数来自请求 query/表单，无需认证即可触达。利用链闭合：source（012.php:5 的 username 参数）→ 字符串拼接（012.php:14）→ 执行汇点 mysqli_query（012.php:15），中间无有效净化，攻击者完全控制 SQL 语义，满足注入成立的全部条件。

修复建议：1) 改用预处理语句与参数绑定：$stmt = mysqli_prepare($link, 'SELECT * FROM `users` WHERE user = ? AND password = ?'); mysqli_stmt_bind_param($stmt, 'ss', $user, $pass); mysqli_stmt_execute($stmt);，彻底消除拼接。2) 若暂不能改造，至少对输入使用 mysqli_real_escape_string 并配合严格白名单（用户名限 [A-Za-z0-9_]{1,32}）。3) 移除或统一收敛 die(mysqli_error(...)) 的原始错误回显，改为记录服务端日志并返回通用错误页。4) 数据库连接使用最小权限账号，禁用 FILE 等不必要权限。5) 口令校验应使用 password_verify 对哈希比对，而非在 SQL 中明文比较。
