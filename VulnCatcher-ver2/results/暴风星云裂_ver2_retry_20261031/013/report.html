F-1 013.php 修改密码处 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.53 · candidate / rule_verified+llm

位置：013.php:29-31

攻击者通过 HTTP 请求提交参数 password_conf（013.php:9 读取），该值被赋给 $pass_new 后直接字符串拼接进 UPDATE 语句：013.php:30 构造 $insert = "UPDATE `users` SET password = '$pass_new' WHERE user = '" . dvwaCurrentUser() . "' LIMIT 1;"，其中 $pass_new 未做任何转义或参数化；随后 013.php:31 通过 mysqli_query($GLOBALS["___mysqli_ston"], $insert) 执行。由于单引号可被注入，攻击者可闭合 password 字段的字符串字面量，改写 SET 子句或追加条件，从而改变 UPDATE 语义。代码中未见 mysqli_real_escape_string、预处理语句或白名单校验，校验完全缺失。

影响：可对 users 表执行任意 UPDATE 语义：篡改任意用户（含 admin）口令实现账户接管/越权登录，或通过布尔/时间盲注逐位读取数据库内容（凭据、用户表数据）造成数据泄露；错误信息经 die(mysqli_error(...)) 回显，进一步辅助报错注入。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达：013.php 为 Web 端点，参数 password_conf 由请求直接提供，无需认证即可到达 013.php:9→30→31 的完整链路；污点从 source 到 mysqli_query 汇点闭合，中间无净化函数，故成立。

修复建议：改用预处理语句：$stmt = $mysqli->prepare("UPDATE `users` SET password = ? WHERE user = ? LIMIT 1"); $stmt->bind_param('ss', $pass_new, dvwaCurrentUser()); 并对 dvwaCurrentUser() 同样参数化；若必须拼接，使用 mysqli_real_escape_string 并配合最小权限数据库账户；关闭 die(mysqli_error()) 的详细错误回显，改为记录日志。

F-2 DVWA 密码修改接口 CAPTCHA 校验可被伪造请求头绕过（硬编码后门值）

high auth_bypass / CWE-287 · 置信度 0.9 · candidate / llm_inferred

位置：013.php:17-31

013.php 在处理密码修改时，CAPTCHA 校验逻辑为 `if ($resp || ($_POST['g-recaptcha-response'] == 'hidd3n_valu3' && $_SERVER['HTTP_USER_AGENT'] == 'reCAPTCHA'))`。攻击者无需真正通过 reCAPTCHA，只需提交固定字符串 `hidd3n_valu3` 作为 g-recaptcha-response，并把 User-Agent 设为 `reCAPTCHA`，即可让整个条件恒真，进入密码修改分支。该分支随后用 md5 处理新密码并执行 UPDATE 语句修改当前用户密码，导致攻击者在不知道原密码、不通过人机校验的情况下重置账户密码，构成认证绕过/账户接管。

影响：攻击者无需通过 CAPTCHA、无需知道原密码即可重置账户密码，导致账户接管；若结合 CSRF 可对受害者静默改密。

CVE/CWE 论证：CWE-287 认证机制不当 / CWE-798 硬编码凭据。外部可通过 HTTP 请求直接触发，条件恒真分支完全由攻击者可控输入决定，利用链闭合。

修复建议：移除硬编码后门值 hidd3n_valu3 及基于 User-Agent 的绕过分支，仅信任 recaptcha_check_answer 的真实返回结果；同时校验原密码。
