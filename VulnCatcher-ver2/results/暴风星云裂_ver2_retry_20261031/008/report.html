F-1 008.php 用户存在性检查处 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.68 · candidate / rule_verified+llm

位置：008.php:21-23

攻击者通过 HTTP 查询参数 user_id 提供输入（008.php:19 读取），该值被直接拼接进 $check_query 字符串："SELECT user_id FROM users WHERE user_id = $id"（008.php:22），随后在 008.php:23 交给 mysqli_query 执行。代码未使用 mysqli_prepare/bind_param，也未对 $id 做类型强制转换（如 intval）或转义，因此单引号、UNION、布尔/时间盲注等载荷可改变 SQL 语义。该查询位于用户存在性检查分支，属于登录/访问流程的前置逻辑，外部无需认证即可触达。

影响：数据库数据泄露（users 表及其他表可被 UNION 读取，包括口令哈希）、通过布尔/时间盲注逐字节提取数据；若数据库账号权限过高，还可导致数据篡改。属于未认证远程 SQL 注入。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达：user_id 来自 HTTP 查询参数；无需认证：检查逻辑在鉴权判定之前执行；利用链闭合：008.php:19 取值 → 008.php:22 字符串拼接 → 008.php:23 mysqli_query 执行，中间无有效净化。

修复建议：改用预处理语句：$stmt = mysqli_prepare($GLOBALS["___mysqli_ston"], "SELECT user_id FROM users WHERE user_id = ?"); mysqli_stmt_bind_param($stmt, "i", $id); 并对 $id 做 intval 白名单校验；同时以最小权限数据库账号运行，关闭详细错误回显。

F-2 008.php 用户信息查询处 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.68 · candidate / rule_verified+llm

位置：008.php:34-36

同一外部输入 user_id（008.php:31 读取）在通过存在性检查后，被再次拼接进 $query："SELECT first_name, last_name, user_id, avatar FROM users WHERE user_id = $id;"（008.php:35），并在 008.php:36 由 mysqli_query 执行。此处同样无参数化、无类型转换、无转义，且查询结果（姓名、头像等）通常会回显到页面，构成可直接回显的注入点。

影响：可读取任意 users 记录字段（first_name/last_name/avatar 等），结合 UNION 可跨表读取敏感数据；回显型注入使数据外带更直接。未认证远程可利用。

CVE/CWE 论证：CWE-89。外部可达：user_id 为 HTTP 查询参数；无需认证：该分支在访问授权判定通过后即执行，而授权判定本身可被前一处注入绕过；利用链闭合：008.php:31 → 008.php:35 拼接 → 008.php:36 执行，无净化。

修复建议：使用 mysqli_prepare + bind_param("i", $id) 参数化；对 $id 做 intval 校验；输出到 HTML 时使用 htmlspecialchars 防止二次问题；数据库账号最小权限。

F-3 008.php 日志写入 INSERT 处 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.63 · candidate / rule_verified+llm

位置：008.php:79-81

在日志记录逻辑中，$log_query 由 {$current_user_id}、{$target_id} 与 '{$ip}' 直接插值拼接而成（008.php:79-80），并在 008.php:81 由 mysqli_query 执行。其中 $target_id 与 $current_user_id 的取值链上游包含外部 user_id 输入（008.php:31），$ip 来自请求环境（如 REMOTE_ADDR 或转发头），均未参数化或转义。攻击者可通过控制 target_id 或伪造 IP 头注入任意 SQL 片段。

影响：可向 bac_log 表写入伪造记录、通过子查询/报错注入读取其他表数据，或利用 INSERT ... SELECT 造成数据污染；若堆叠查询被驱动允许，影响进一步扩大。未认证远程可利用。

CVE/CWE 论证：CWE-89。外部可达：target_id 源自 user_id 参数链，$ip 源自请求头；无需认证：日志写入在业务分支内自动触发；利用链闭合：008.php:31 → 008.php:79-80 字符串插值 → 008.php:81 执行，无净化。

修复建议：对 INSERT 使用预处理语句并绑定 (user_id, target_id, ip_address) 三个参数；$ip 使用 filter_var(FILTER_VALIDATE_IP) 校验并只信任受控代理头；对 id 类字段强制 intval；数据库账号仅授予 INSERT 所需列权限。

F-4 DVWA 008.php 通过可篡改的 user_id Cookie 实现越权访问任意用户资料（BAC/IDOR）

high idor / CWE-639 · 置信度 0.85 · candidate / llm_inferred

位置：008.php:30-47

008.php 的访问控制完全依赖客户端 Cookie `user_id`：脚本读取 `$_COOKIE['user_id']` 并仅用 `intval()` 转换后与请求参数 `user_id` 比较（第 30-33 行），相等即放行并查询该用户资料（第 35-47 行）。服务端从未将 Cookie 与当前登录会话（`dvwaCurrentUser()` 查得的 `$current_user_id`）绑定，攻击者只需把 Cookie 改成目标用户 ID 即可读取任意用户 first_name/last_name/avatar。这是典型的失效访问控制/IDOR（CWE-639/CWE-284）。

影响：任意已登录用户可枚举并读取所有用户（含管理员）的姓名、头像等资料，构成水平/垂直越权信息泄露。

CVE/CWE 论证：CWE-639 授权绕过；外部单请求可达，无需高权限，链路在 008.php 内闭合。

修复建议：服务端应使用会话中的 $current_user_id 做归属校验，忽略客户端 Cookie 中的 user_id；对敏感资料查询强制 WHERE user_id = $current_user_id。
