F-1 009.php 用户存在性检查 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：009.php:20-22

攻击者通过 HTTP 查询参数 `user_id`（009.php:17 读取）传入任意字符串，该值未经转义或参数化即被拼接进 `$check_query = "SELECT user_id FROM users WHERE user_id = '$id'"`（009.php:21），随后在 009.php:22 由 `mysqli_query($GLOBALS["___mysqli_ston"], $check_query)` 执行。由于 `$id` 被单引号包裹但未做 `mysqli_real_escape_string` 或预处理绑定，攻击者可闭合单引号注入任意 SQL 片段（如 `1' OR '1'='1`、`1' UNION SELECT ...`）。该查询是后续逻辑的前置判断，注入结果直接决定 `$user_exists` 分支走向，因此可被用于布尔盲注或联合查询读取任意表数据。

影响：数据库数据泄露：可读取 users 表及其他库表内容（用户名、口令哈希、个人信息）；结合后续查询可进一步枚举/篡改数据；若数据库账户权限过高，可能读写文件或造成数据完整性破坏。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达：`user_id` 来自 HTTP 查询参数，无需认证即可触发；利用链闭合：009.php:17 取值 → 009.php:21 字符串拼接 → 009.php:22 mysqli_query 执行，中间无白名单、类型转换或参数化，校验无效。

修复建议：改用预处理语句：`$stmt = $mysqli->prepare('SELECT user_id FROM users WHERE user_id = ?'); $stmt->bind_param('i', $id); $stmt->execute();`；同时对 `$id` 做整型强制转换（`$id = (int)$_GET['user_id']`）作为纵深防御；数据库账户遵循最小权限，禁止 FILE 权限。

F-2 009.php 用户详情查询 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：009.php:27-29

同一外部输入 `user_id`（009.php:17）在通过存在性检查后，被再次拼接进 `$query = "SELECT first_name, last_name, user_id, avatar FROM users WHERE user_id = '$id';"`（009.php:28），并在 009.php:29 由 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。`$id` 未转义、未参数化，攻击者可用 `1' UNION SELECT ...` 直接控制结果集，将任意表字段映射到 first_name/last_name/avatar 输出位置，实现数据外带。

影响：数据库数据泄露：通过 UNION 注入把任意表（如凭据表）内容回显到页面字段，导致敏感信息泄露；也可用于报错注入获取库结构。

CVE/CWE 论证：CWE-89。外部可达：`user_id` 为 HTTP 查询参数，无需认证；利用链闭合：009.php:17 → 009.php:28 拼接 → 009.php:29 执行，无有效净化。注意该注入点位于 `$user_exists` 为真的分支内，攻击者可用恒真条件（如 `1' OR '1'='1`）同时满足前置检查与本次查询。

修复建议：使用预处理语句绑定 `user_id` 整型参数；对输出字段做 HTML 转义；限制数据库账户权限；对 `user_id` 做严格数字白名单校验。

F-3 009.php 日志写入 INSERT 语句 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.68 · candidate / rule_verified+llm

位置：009.php:71-73

009.php:71-72 构造 `$log_query = "INSERT INTO bac_log (user_id, target_id, ip_address) VALUES ({$current_user_id}, {$target_id}, '{$ip}')"`，其中 `{$current_user_id}`、`{$target_id}` 为无引号数值位，`'{$ip}'` 为引号包裹的字符串位，均未转义，随后在 009.php:73 由 `mysqli_query($GLOBALS["___mysqli_ston"], $log_query)` 执行。`$target_id` 与 `$current_user_id` 源自同一外部 `user_id` 输入链路（009.php:17），`$ip` 通常来自 `REMOTE_ADDR` 或可伪造头。攻击者可在数值位直接注入（如 `1),(1,1,(SELECT ...))-- -`）或闭合 `$ip` 单引号注入，实现堆叠/子查询注入。

影响：数据库写入被污染，可插入伪造日志、通过子查询外带数据（盲注/报错注入），并可能破坏审计日志完整性；若驱动允许堆叠语句，可进一步执行任意 SQL。

CVE/CWE 论证：CWE-89。外部可达：`target_id`/`user_id` 来自 HTTP 参数，`ip` 可能来自请求头，无需认证；利用链闭合：009.php:17 → 009.php:71-72 拼接 → 009.php:73 执行，无参数化。该点置信度略低于前两处，因 `$current_user_id`、`$target_id`、`$ip` 的具体赋值行未在片段中给出，但拼接与执行证据明确。

修复建议：使用预处理语句绑定 user_id、target_id、ip_address 三个参数；对数值字段强制整型转换；`$ip` 使用 `filter_var($ip, FILTER_VALIDATE_IP)` 校验后再绑定；审计日志表使用独立最小权限账户。
