F-1 019.php 未过滤的 $_POST['include'] 直接拼接进页面输出（CWE-22 路径穿越/任意文件包含）

high path_traversal / CWE-22 · 置信度 0.78 · candidate / rule_verified+llm

位置：019.php:8-10

攻击者通过 HTTP POST 提交参数 include（019.php:8 的 isset($_POST['include']) 判断存在性，019.php:10 读取其值）。该值未经任何白名单、basename()、realpath() 规范化或路径前缀校验，被直接以字符串拼接方式写入 $page['body'] 的内联表达式（019.php:10：" . $_POST['include'] . "）。由于该拼接结果随后作为页面内容/包含目标使用，攻击者可提交 ../ 序列或绝对路径穿越预期目录，读取或引入任意文件。校验无效的原因：代码只做了 isset() 存在性检查，没有任何内容过滤或路径规范化，属于典型的“存在性检查被误当作安全校验”。

影响：任意文件读取/本地文件包含：可读取 Web 根目录之外的敏感文件（配置、凭据、系统文件），若被包含的 PHP 文件可解析则可能导致代码执行；也可用于探测服务器文件系统结构，为后续攻击提供信息。

CVE/CWE 论证：CWE-22（路径穿越）。外部可达性：019.php 为可直接 HTTP 访问的脚本，POST 参数 include 无需认证即可提交；利用链闭合：source（$_POST['include']，019.php:8/10）→ 无净化拼接（019.php:10）→ 危险汇点（页面输出/包含）。无需前置权限，攻击复杂度低。

修复建议：1) 不要将用户输入直接拼接进包含路径或页面输出；2) 使用固定白名单映射（如 $allowed = ['home','about']; 仅接受白名单键）；3) 若必须使用文件名，先 basename() 去除目录部分，再用 realpath() 规范化并校验结果仍位于允许的基目录内；4) 对输出到 HTML 的内容使用 htmlspecialchars() 编码；5) 关闭 allow_url_include，限制 open_basedir。
