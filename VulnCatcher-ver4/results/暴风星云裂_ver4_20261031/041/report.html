F-1 041.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：041.php:9-11

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（041.php:5 读取该参数），该值未经任何过滤、转义或类型校验，被直接拼接进 SQL 语句：041.php:10 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id';"`，其中 `$id` 位于单引号字符串字面量内部；随后 041.php:11 调用 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行该语句。由于未使用 mysqli 预处理语句/参数绑定，也未调用 mysqli_real_escape_string 等转义函数，攻击者只需在 `id` 中闭合单引号即可改变查询语义（例如 `1' OR '1'='1` 返回全部用户，或使用 UNION SELECT 读取其他表数据）。此外 041.php:11 在查询失败时通过 `die(... mysqli_error(...) ...)` 将数据库错误信息回显到页面，为基于报错的注入提供了反馈通道，进一步降低利用门槛。

影响：数据库数据泄露：攻击者可读取 users 表之外的任意表（如账号、口令散列等），并可结合 UNION/布尔/报错注入逐字节提取数据；在数据库账号权限较高且支持堆叠查询的场景下可能进一步导致数据篡改或写入文件。错误回显还会泄露库名、表结构等元信息。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素的不当中和）。外部可达性：注入点为 HTTP query 参数 `id`（041.php:5），无需认证即可访问该脚本；利用链闭合：外部输入 → `$id` → 字符串拼接 `$query`（041.php:10）→ `mysqli_query` 执行（041.php:11），全程无净化函数，且错误信息回显（041.php:11 的 die/mysqli_error）提供注入结果反馈。

修复建议：改用参数化查询：`$stmt = $mysqli->prepare("SELECT first_name, last_name FROM users WHERE user_id = ?"); $stmt->bind_param('i', $id); $stmt->execute();`，并对 `id` 做整型强校验（如 `filter_var($id, FILTER_VALIDATE_INT)`）。禁止将外部输入拼接进 SQL 字符串；关闭生产环境的数据库错误回显（记录到日志而非输出到页面）；数据库账号遵循最小权限，仅授予所需表的 SELECT 权限。
