F-1 021.php 中 $_POST['include'] 未净化即拼接进页面 body（CWE-22 路径/内容注入）

high path_traversal / CWE-22 · 置信度 0.4 · candidate / rule_verified+llm

位置：021.php:12-14

证据仅覆盖 021.php 第 12-14 行：第 14 行 `if (isset ($_POST['include'])) {` 只判断 POST 参数 include 是否存在，随后（第 15-16 行，见相邻候选）把 `$_POST['include']` 直接拼进 `$page['body']`。攻击者通过 POST 参数 include 提交任意字符串，代码未做白名单、basename、realpath 规范化或路径前缀校验。需要说明的是：本条候选的 source 被标注为 query `include`，但源码实际读取的是 `$_POST['include']`（POST 体参数），注入点应记为 POST 参数 include，而非 URL query。此外，第 14 行本身只是 isset 判断，真正的危险汇点是第 16 行的字符串拼接；本条候选把 isset 行当作 sink，证据链不完整，实际危害需结合 GEN-11054cd96202 一起判断。

影响：取决于拼接结果最终如何被使用：若 `$page['body']` 被写入模板/文件或以 include/require 方式加载，则可导致任意本地文件读取或任意文件写入（路径穿越）；若仅回显到 HTML，则退化为反射型内容注入（XSS）。当前证据只到字符串拼接，未给出后续 include/file_put_contents 等消费点，因此不能断言已构成任意文件读写。

CVE/CWE 论证：CWE-22（路径穿越）。外部可达性：021.php 为可直接请求的 PHP 页面，POST 参数无需认证即可提交。但利用链未闭合——证据中缺少 `$page['body']` 之后的文件系统或 include 消费点，无法证明穿越到任意路径，故仅按 llm_inferred 记录，不主张 CVE 级结论。

修复建议：1) 不要用用户输入拼接路径或页面内容；若必须按名加载页面，使用固定白名单映射（如 `['home'=>'home.php', ...]`）并只接受映射内键；2) 对路径使用 `basename()` + `realpath()` 并与允许根目录做前缀比较；3) 输出到 HTML 时使用 `htmlspecialchars($v, ENT_QUOTES, 'UTF-8')` 编码；4) 禁止把 `$_POST` 值直接拼进 include/require 或文件写入函数。

F-2 021.php POST 参数 include 未编码直接拼接进页面导致反射型 XSS（CSP nonce 可复用绕过）

medium xss / CWE-79 · 置信度 0.85 · candidate / llm_inferred

位置：021.php:14-18

021.php 第 14-18 行读取 $_POST['include']，未做任何 HTML 实体编码或过滤，直接以字符串拼接方式追加到 $page['body']，随后该 body 被输出到响应页面（第 19-25 行继续拼接表单，说明 $page['body'] 为页面渲染内容）。攻击者提交包含 <script> 的 include 值即可在受害者浏览器执行任意脚本。虽然第 3-5 行设置了 CSP script-src 'self' 'unsafe-inline' 'nonce-TmV2ZXIgZ29pbmcgdG8gZ2l2ZSB5b3UgdXA='，但该 nonce 是硬编码常量且第 10 行注释直接给出了可用示例 <script nonce="TmV2ZXIgZ29pbmcgdG8gZ2l2ZSB5b3UgdXA=">alert(1)</script>，攻击者可直接复用该 nonce 绕过 CSP；同时第 8 行显式设置 X-XSS-Protection: 0 关闭了浏览器 XSS 过滤器。

影响：反射型 XSS，可在受害者浏览器上下文执行任意 JS，窃取会话/发起敏感操作；CSP 因硬编码 nonce 失效，X-XSS-Protection 被关闭。

CVE/CWE 论证：CWE-79。外部无需认证即可通过 POST include 参数注入脚本，链闭合：source($_POST['include'])→拼接→页面输出；CSP 硬编码 nonce 与 X-XSS-Protection:0 使防护失效。

修复建议：对 $_POST['include'] 使用 htmlspecialchars($v, ENT_QUOTES, 'UTF-8') 输出；移除硬编码 nonce，改为每次请求随机生成；移除 X-XSS-Protection: 0。

F-3 021.php 第 3 行 CSP 同时启用 'unsafe-inline' 与固定 nonce，策略被削弱（CWE-693）

medium csp / CWE-693 · 置信度 0.6 · candidate / rule_verified+llm

位置：021.php:2-3

证据为 021.php 第 2-3 行：`$headerCSP = "Content-Security-Policy: script-src 'self' 'unsafe-inline' 'nonce-TmV2ZXIgZ29pbmcgdG8gZ2l2ZSB5b3UgdXA=';";`。该策略在 script-src 中同时声明 `'unsafe-inline'` 和一个硬编码 nonce。按 CSP 规范，当存在 nonce 或 hash 源时，`'unsafe-inline'` 会被忽略；但此处 nonce 值是写死在源码中的常量（base64 解码为 “Never going to give you up”），任何能读取源码或该响应头的攻击者都可复用同一 nonce，使 nonce 机制形同虚设。同时策略未包含 `object-src 'none'`、`base-uri 'none'`、`default-src` 等兜底指令。

影响：CSP 作为纵深防御被削弱：一旦页面存在 HTML 注入点（例如同文件第 16 行把 `$_POST['include']` 拼入 body），攻击者可用已知固定 nonce 的内联脚本绕过 script-src 限制执行任意 JS，导致会话窃取、CSRF 令牌读取、页面内容篡改。该问题本身不直接造成 RCE，属于防护失效类缺陷。

CVE/CWE 论证：CWE-693（防护机制失效）。外部可达性：任意访问 021.php 的响应都会带上该 CSP 头，无需认证。但这是配置型弱点，不构成独立可利用漏洞；其危害依赖同文件的内容注入点（GEN-11054cd96202）是否被实际消费到响应中，证据中该消费点缺失，故利用链未完全闭合。

修复建议：1) 移除 `'unsafe-inline'`，改用每次请求随机生成的高熵 nonce（如 `base64_encode(random_bytes(16))`）并同步写入对应 `<script nonce=...>`；2) 不要硬编码 nonce；3) 补充 `default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`；4) 将 CSP 作为纵深防御而非唯一防线，同时修复第 16 行的输入拼接问题。
