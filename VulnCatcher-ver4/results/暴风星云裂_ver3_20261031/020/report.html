F-1 020.php 中 $_POST['include'] 直接拼入 <script src> 的属性注入 / 脚本源可控（CWE-79/CWE-116）

high path_traversal / CWE-22 · 置信度 0.55 · candidate / rule_verified+llm

位置：020.php:13-15

020.php:13-15 显示：`if (isset ($_POST['include'])) {` 后执行 `$page['body'] .= "\n\t<script src='" . $_POST['include'] . "'></script>"`。外部 POST 参数 `include` 未经任何编码或校验，被直接拼接进 HTML 的 `<script src='...'>` 单引号属性中。攻击者可在参数值中闭合单引号并注入任意属性或标签（例如 `x' onerror='...` 或 `'></script><script>...`），从而在受害者浏览器中执行脚本。注意：该汇点是 HTML/JS 输出上下文，性质为 XSS/HTML 注入，而非路径穿越；候选将其标为 path_traversal 属于类型误判。

影响：反射型 XSS：攻击者构造带恶意 `include` 参数的 POST 请求（或借助自动提交表单）诱导受害者访问，可在站点源下执行任意 JavaScript，窃取会话 Cookie、发起 CSRF 操作、篡改页面内容。由于该值同时被用作脚本 src，还可让页面从攻击者指定域加载脚本（受 CSP 约束，见 SEM-582e93de1b73）。

CVE/CWE 论证：CWE-79（跨站脚本）/CWE-116（输出编码不当）。外部可达性：`$_POST['include']` 为匿名可提交参数，无需认证；利用链闭合：输入 → 字符串拼接 → 写入 `$page['body']` → 输出到响应 HTML 的 script 标签属性，中间无编码或白名单。

修复建议：输出到 HTML 属性前使用 `htmlspecialchars($v, ENT_QUOTES, 'UTF-8')` 进行上下文编码；对脚本来源使用固定白名单（仅允许已知 CDN 主机名）而非任意用户输入；优先改为服务端映射的固定脚本路径，避免把用户输入放进 src。

F-2 020.php 通过 POST 参数 include 反射注入 script src，CSP 白名单可被绕过导致任意脚本执行

medium xss / CWE-79 · 置信度 0.87 · candidate / llm_inferred

位置：020.php:13-17

020.php 第 13-17 行在收到 POST 参数 include 时，未做任何 HTML 属性编码或 URL 白名单校验，直接把 $_POST['include'] 拼进 <script src='...'> 的单引号属性中。攻击者可闭合单引号并注入任意属性/标签，或直接指向 CSP 白名单内可托管任意 JS 的域（pastebin.com、hastebin.com、unpkg.com、cdn.jsdelivr.net、digi.ninja 等），从而在受害者浏览器执行任意脚本。第 3-5 行设置的 CSP 明确把上述域列入 script-src，等于为攻击者提供了合法的脚本托管源，CSP 无法阻止利用。

影响：在受害者浏览器上下文执行任意 JavaScript，可窃取会话、伪造请求、篡改页面内容；CSP 因白名单域可托管任意脚本而失效。

CVE/CWE 论证：CWE-79 反射型 XSS。外部无需认证即可通过 POST 触发，输入直达 HTML 输出汇点，链闭合；CSP 白名单域（jsdelivr/unpkg/pastebin 等）可被攻击者用于托管脚本，属典型 CSP 绕过。

修复建议：对 include 做严格 URL 白名单校验（仅允许受控域），输出时使用 htmlspecialchars 对属性值编码，并收紧 CSP 至不可托管任意内容的源。

F-3 020.php 中过于宽松的 CSP script-src 白名单（CWE-693）

medium csp / CWE-693 · 置信度 0.6 · candidate / rule_verified+llm

位置：020.php:2-3

020.php:3 定义 `$headerCSP = "Content-Security-Policy: script-src 'self' https://pastebin.com hastebin.com www.toptal.com example.com code.jquery.com https://ssl.google-analytics.com unpkg.com cdn.jsdelivr.net digi.ninja ;"`。该策略把多个第三方内容托管域（pastebin.com、hastebin.com、unpkg.com、cdn.jsdelivr.net、example.com 等）加入 script-src 白名单，其中 pastebin/hastebin/unpkg/jsdelivr 允许用户上传或托管任意 JS 内容，等于为攻击者提供了合法的脚本加载源。结合 020.php:15 中 `$_POST['include']` 直接进入 `<script src>`，攻击者只需把 src 指向这些白名单域上的恶意脚本即可绕过 CSP。片段未显示该 header 是否真正通过 `header()` 输出，也未显示 nonce/hash 或 `'strict-dynamic'` 的使用。

影响：CSP 防护形同虚设：在存在 020.php:15 的属性注入/脚本源可控问题时，攻击者可借助白名单内的用户内容托管域加载任意脚本，实现持久或反射型脚本执行，削弱对 XSS 的纵深防御。

CVE/CWE 论证：CWE-693（防护机制失效）。外部可达性：CSP 随响应头下发，任何访问者均受影响；无需认证。利用链闭合性：策略文本本身已确认包含可托管任意 JS 的第三方域，与 020.php:15 的可控 src 形成组合；但 header 实际下发位置在片段中未给出，属证据缺口。

修复建议：收紧 script-src：移除 pastebin/hastebin/unpkg/jsdelivr 等用户内容托管域，仅保留确需的固定版本资源域；引入 nonce 或 hash 并配合 `'strict-dynamic'`；对 020.php:15 的 src 使用服务端白名单映射，禁止用户直接控制脚本 URL；同时补充 `object-src 'none'`、`base-uri 'none'`。
