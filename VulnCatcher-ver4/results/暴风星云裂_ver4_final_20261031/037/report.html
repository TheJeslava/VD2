F-1 037.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：037.php:11-13

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入，该值在 037.php:5 被读取后未做任何类型校验、转义或参数化，直接以字符串拼接方式嵌入 037.php:11 的 SQL 语句：`SELECT first_name, last_name FROM users WHERE user_id = '$id' LIMIT 1;`。由于 `$id` 被单引号包裹但未经过 mysqli_real_escape_string 或预处理语句处理，攻击者可闭合单引号并注入任意 SQL 片段（如 `1' OR '1'='1` 或 UNION 查询）。拼接完成的 `$query` 在 037.php:13 传入 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行，构成完整的 source→sink 污点链。代码注释显示已移除 `or die` 以抑制 MySQL 错误回显，说明开发者有意隐藏报错，但这并不构成任何净化，注入依然成立，只是错误型注入的可见性被降低。

影响：数据库查询逻辑可被任意篡改：可绕过 user_id 条件读取 users 表全部记录（first_name、last_name 等），可通过 UNION 注入读取其他表（如用户名/口令哈希），可结合堆叠或盲注进一步枚举库结构。属于数据泄露与数据库层面的越权读取，严重程度 critical。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素的不当中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问该脚本；利用链闭合：037.php:5 读取输入 → 037.php:11 字符串拼接 → 037.php:13 mysqli_query 执行，中间无白名单、无转义、无参数化，攻击者单次请求即可控制 SQL 语义。

修复建议：改用预处理语句与参数绑定：`$stmt = $GLOBALS["___mysqli_ston"]->prepare("SELECT first_name, last_name FROM users WHERE user_id = ? LIMIT 1"); $stmt->bind_param('i', $id); $stmt->execute();`，并将 `$id` 强制转换为整数（`$id = (int)$_GET['id'];`）。若必须使用字符串拼接，至少使用 mysqli_real_escape_string 并配合类型白名单校验；同时恢复受控的错误处理（记录到服务端日志而非回显给客户端），并对数据库账号实施最小权限。
