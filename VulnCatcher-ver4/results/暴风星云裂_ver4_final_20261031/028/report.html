攻击者通过 HTTP 查询参数 `page` 提供输入，该输入在 028.php:4 被赋给变量 `$file`。028.php:7 的校验为 `if( !fnmatch( "file*", $file ) && $file != "include.php" )`，其逻辑是：只要 `$file` 匹配 `file*` 模式，或者等于字面量 `include.php`，就放行。`fnmatch` 的 `file*` 模式只约束字符串前缀，不阻止路径分隔符与上跳序列，因此 `file../../etc/passwd`、`file/../../../../etc/passwd` 之类取值既满足 `file*` 前缀匹配，又携带 `../` 穿越片段，校验被绕过。校验失败分支（第 7 行之后）的具体处理代码未在给定片段中展示，因此最终文件操作语句（include/require 或文件读取函数）的确切行号证据不足；但候选已将该行标注为 path_traversal 汇点，且 exploit_chain 显示污点从 `$file` 直达该判断，未发现其他净化（无 realpath、无 basename、无白名单枚举）。

影响：若第 7 行之后的放行分支将 `$file` 用于 include/require，则可包含服务器上任意可读文件：读取 /etc/passwd、应用配置文件、数据库凭据等敏感数据（信息泄露）；若可写入日志或上传文件，还可进一步组合为本地文件包含到 RCE。若用于文件读取函数，则为任意文件读取。具体危害等级取决于未展示的汇点调用，当前证据支持“任意文件读取/包含”这一类影响。

CVE/CWE 论证：CWE-22（路径穿越）。外部可达性：入口为 HTTP query 参数 `page`（028.php:4），无需认证即可触达。利用链闭合度：source（`page`）→ 变量 `$file` → 校验 `fnmatch("file*", $file)`（028.php:7）→ 放行分支。前缀匹配型校验对 `../` 无效，属于典型的黑名单/前缀校验失效。缺口：第 7 行之后实际执行文件操作的语句未在 code_pack 片段中给出，因此“最终危险操作”的具体函数名与行号证据不足，利用链末端为推断。

修复建议：1) 不要用 `fnmatch("file*", ...)` 这类前缀匹配做安全校验；改为白名单枚举，例如 `$allowed = ['include.php','file1.php','file2.php']; if(!in_array($file, $allowed, true)) { http_response_code(400); exit; }`。2) 若必须按目录取文件，先 `$base = realpath(__DIR__.'/pages'); $target = realpath($base.'/'.basename($file));`，再校验 `strpos($target, $base.DIRECTORY_SEPARATOR) === 0`，否则拒绝。3) 使用 `basename()` 剥离路径分隔符，拒绝包含 `..`、`/`、`\`、空字节的输入。4) 以最小权限运行 Web 进程，限制可读目录范围，避免包含路径落在敏感配置目录。
