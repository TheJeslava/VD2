F-1 009.php 用户存在性检查 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：009.php:20-22

攻击者通过 HTTP 请求的 query 参数 `user_id` 提供输入，该值在 009.php:17 被读取后赋给变量 `$id`，未经任何转义或参数化，直接在 009.php:21 拼接进 SQL 语句 "SELECT user_id FROM users WHERE user_id = '$id'"，并在 009.php:22 通过 mysqli_query($GLOBALS["___mysqli_ston"], $check_query) 执行。由于 `$id` 被单引号包裹但未使用 mysqli_real_escape_string 或预处理语句，攻击者可闭合单引号注入任意 SQL 片段（如 `1' OR '1'='1` 或 UNION 查询）。该查询是后续逻辑（用户是否存在判断）的前置检查，注入结果直接影响分支走向。

影响：可读取 users 表及同库其他表的任意数据（如凭据、个人信息），并可借助 UNION/布尔盲注枚举数据库结构；若数据库账户权限过高，还可能造成数据篡改。属于机密性与完整性破坏。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达：`user_id` 来自 HTTP query 参数，无需认证即可触发；利用链闭合：009.php:17 取值 → 009.php:21 字符串拼接 → 009.php:22 mysqli_query 执行，中间无有效净化。

修复建议：改用预处理语句：`$stmt = $mysqli->prepare("SELECT user_id FROM users WHERE user_id = ?"); $stmt->bind_param('s', $id); $stmt->execute();`；若必须动态拼接，至少使用 mysqli_real_escape_string 并对 `user_id` 做类型/白名单校验（如强制整数）。

F-2 009.php 用户信息查询 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：009.php:27-29

同一外部输入 `user_id`（009.php:17 读取，赋给 `$id`）在通过存在性检查后，于 009.php:28 被再次拼接进 "SELECT first_name, last_name, user_id, avatar FROM users WHERE user_id = '$id';"，并在 009.php:29 由 mysqli_query 执行。该处同样未使用参数化或转义，单引号包裹的 `$id` 可被闭合注入。由于该查询返回用户资料字段，注入可直接操纵返回结果集。

影响：可泄露 users 表的 first_name、last_name、user_id、avatar 等字段，配合 UNION 可读取任意表数据；也可通过注入改变查询逻辑以越权获取其他用户资料。

CVE/CWE 论证：CWE-89。外部可达：`user_id` 为 HTTP query 参数，无需认证；利用链闭合：009.php:17 → 009.php:28 拼接 → 009.php:29 mysqli_query，无净化。

修复建议：使用预处理语句绑定 `$id`；对 `user_id` 做整数强制转换或白名单校验；避免将外部输入直接插入 SQL 字符串。

F-3 009.php 日志写入 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.68 · candidate / rule_verified+llm

位置：009.php:71-73

009.php:71-72 构造 INSERT 语句 "INSERT INTO bac_log (user_id, target_id, ip_address) VALUES ({$current_user_id}, {$target_id}, '{$ip}')"，其中 `$target_id` 与 `$ip` 未加引号/未转义直接拼接，`$current_user_id` 亦为变量拼接；该语句在 009.php:73 由 mysqli_query 执行。候选标注 source 为 query `user_id`（009.php:17），但代码片段显示 `$target_id`、`$ip`、`$current_user_id` 才是直接进入该 INSERT 的变量，`user_id` 到 `$target_id` 的赋值关系在给定片段中未直接呈现，故污点链存在证据缺口。若 `$target_id` 或 `$ip` 可由外部控制（如来自请求参数或可伪造的 IP 头），则可注入。

影响：若注入成立，可向 bac_log 表写入任意数据或通过子查询/报错注入读取其他表数据，破坏日志完整性与数据库机密性。

CVE/CWE 论证：CWE-89。外部可达性：取决于 `$target_id`/`$ip`/`$current_user_id` 的来源，给定片段未展示其赋值，证据不足；利用链：009.php:71-72 拼接 → 009.php:73 执行，净化缺失可确认，但 source 到 sink 的完整路径未在片段中闭合。

修复建议：对 INSERT 使用预处理语句并绑定所有列值；`$ip` 应通过 `filter_var($_SERVER['REMOTE_ADDR'], FILTER_VALIDATE_IP)` 校验后再入库；`$target_id`、`$current_user_id` 强制转为整数。

F-4 DVWA 009.php 用户资料接口通过硬编码 token 绕过访问控制导致越权读取任意用户资料

high idor / CWE-639 · 置信度 0.85 · candidate / llm_inferred

位置：009.php:26-40

009.php 的 action/user_id 分支仅用 `$_GET['token'] == 'user_token'` 这一硬编码字符串作为访问控制，且该 token 直接写在页面注释提示中（第 39、46 行）。攻击者无需任何身份即可传入 token=user_token 并遍历 user_id，读取任意用户的 first_name、last_name、avatar 等资料，构成水平/垂直越权（IDOR）。

影响：未授权读取任意用户姓名、头像等敏感资料，越权访问

CVE/CWE 论证：CWE-639 授权绕过/IDOR；无需认证，token 硬编码且泄露，链闭合

修复建议：移除硬编码 token，改为服务端会话身份校验并校验对象归属
