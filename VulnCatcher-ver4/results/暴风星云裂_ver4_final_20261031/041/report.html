F-1 041.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.83 · candidate / rule_verified+llm

位置：041.php:9-11

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入，该值在 041.php:5 被读取后，于 041.php:10 直接以字符串拼接方式嵌入 SQL 语句：`$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id';";`，随后在 041.php:11 交由 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。代码中未对 `$id` 做类型转换（如 intval）、转义（如 mysqli_real_escape_string）或参数化处理，单引号闭合即可改变查询语义，因此校验无效。此外 041.php:11 的 `or die(... mysqli_error(...) ...)` 会把数据库错误信息回显到响应中，为报错型注入和盲注提供反馈通道。

影响：数据库查询语句可被任意篡改：可 UNION 查询同库其他表（如 users 表的 user/password 字段）导致凭据等敏感数据泄露；可基于布尔/时间盲注逐字节提取数据；在数据库账户权限较高且支持堆叠查询的环境下可能进一步写入或破坏数据。错误信息回显降低了利用门槛。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问该脚本；利用链闭合：source（041.php:5 的 `id`）→ 字符串拼接（041.php:10）→ 执行汇点 `mysqli_query`（041.php:11），中间无任何净化函数，攻击者仅需构造 `id=1' OR '1'='1` 之类的值即可改变查询逻辑。证据等级为源码推断（llm_inferred），未做动态验证。

修复建议：改用预处理语句与参数绑定：`$stmt = $mysqli->prepare("SELECT first_name, last_name FROM users WHERE user_id = ?"); $stmt->bind_param('i', $id);`，并对 `id` 做整型强校验（如 `filter_var($id, FILTER_VALIDATE_INT)`）。禁止将用户输入拼接进 SQL；关闭数据库错误详情回显（生产环境记录日志而非 `die(mysqli_error())`）；数据库账户遵循最小权限，仅授予所需表的 SELECT 权限。
