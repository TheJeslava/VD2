F-1 013.php 修改密码功能 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.55 · candidate / rule_verified+llm

位置：013.php:29-31

攻击者通过修改密码表单提交新口令，该值在 013.php:8 由 query `password_new` 读入，经 013.php:26 的 mysqli_real_escape_string 转义后，在 013.php:27 被 md5() 处理，随后在 013.php:30 直接拼接进 UPDATE 语句：$insert = "UPDATE `users` SET password = '$pass_new' WHERE user = '" . dvwaCurrentUser() . "' LIMIT 1;"，并在 013.php:31 交给 mysqli_query 执行。关键点在于转义发生在 md5() 之前：mysqli_real_escape_string 对原始输入中的引号加反斜杠，但 md5() 会把整串（含反斜杠）哈希成 32 位十六进制字符，反斜杠随之消失，因此进入 SQL 的 $pass_new 是纯 [0-9a-f] 字符串，看似安全；然而同一流程中若存在未走 md5 的分支或 dvwaCurrentUser() 返回值被污染，则拼接仍可被突破。就本片段可见证据而言，$pass_new 经 md5 后不含引号，直接注入该变量不可行，真正的注入面在于 dvwaCurrentUser() 的返回值被直接拼接进 WHERE 子句且无任何转义/参数化（013.php:30），以及错误信息经 die(mysqli_error(...)) 回显（013.php:31）构成报错型注入的信息泄露通道。

影响：若 dvwaCurrentUser() 的取值可被外部影响（如会话中的用户名、Cookie 派生值），攻击者可构造 user 条件逃逸，实现任意用户口令重置（UPDATE users SET password=... WHERE user='...' OR '1'='1'），导致全站账户接管；同时 013.php:31 将 mysqli_error 原文回显到页面，可被用于报错注入逐位提取数据库内容（库名、表名、users 表口令哈希），造成敏感数据泄露。

CVE/CWE 论证：CWE-89：SQL 命令中特殊元素未正确中和。外部可达性：该逻辑位于修改密码的 HTTP 处理路径，表单参数 password_new/password_conf 由远程用户提交，无需认证即可访问 DVWA 低安全级别页面（会话内即可）。利用链闭合度：source（013.php:8 的 password_new）→ 拼接（013.php:30）→ sink（013.php:31 mysqli_query）路径完整；但 md5() 位于转义与拼接之间，削弱了 password_new 直接注入的可利用性，故本条按 llm_inferred 记录，需运行时确认 dvwaCurrentUser() 是否可控。

修复建议：1) 全面改用预处理语句：$stmt = mysqli_prepare($link, 'UPDATE users SET password = ? WHERE user = ? LIMIT 1'); mysqli_stmt_bind_param($stmt, 'ss', $pass_new, dvwaCurrentUser()); 2) 不要依赖 mysqli_real_escape_string 与 md5 的顺序巧合，任何进入 SQL 的值都必须参数化；3) 关闭错误回显，将 mysqli_error 写入服务端日志而非 die() 输出到页面；4) 口令哈希改用 password_hash()/password_verify()（PASSWORD_DEFAULT），并在服务端校验 password_new 与 password_conf 一致、长度与字符集白名单；5) 对 dvwaCurrentUser() 的返回值做来源确认，确保其只来自服务端会话且不可由请求参数覆盖。

F-2 DVWA 密码修改页 CAPTCHA 校验可被伪造请求头绕过（013.php）

high auth_bypass / CWE-287 · 置信度 0.9 · candidate / llm_inferred

位置：013.php:17-23

013.php 在处理密码修改时，先调用 recaptcha_check_answer 校验第三方 CAPTCHA，但校验条件写成 `$resp || (g-recaptcha-response == 'hidd3n_valu3' && HTTP_USER_AGENT == 'reCAPTCHA')`。攻击者只要把 POST 参数 g-recaptcha-response 设为固定字符串 hidd3n_valu3，并把 User-Agent 头设为 reCAPTCHA，即可让整个 if 条件恒真，完全跳过 CAPTCHA 校验，随后直接进入密码修改逻辑（第 25-31 行），把当前登录用户的密码改为攻击者指定值。这是硬编码的万能口令 + 可伪造请求头构成的认证辅助机制绕过（CWE-287 / CWE-798），属于 DVWA 中已知的 CAPTCHA bypass 场景。

影响：攻击者无需通过真实 CAPTCHA 即可修改账户密码；结合 CSRF 可诱导受害者改密，导致账户接管。

CVE/CWE 论证：CWE-287 认证机制不当 / CWE-798 硬编码凭据。外部可达、仅需低权限登录，利用链在源码中完整闭合（第 17-23 行条件恒真 → 第 25-31 行改密）。

修复建议：移除硬编码万能值 hidd3n_valu3 与 User-Agent 判断，仅以 recaptcha_check_answer 返回值为准；CAPTCHA 校验失败必须终止流程。

F-3 013.php 使用 MD5 存储口令（CWE-328 弱哈希）

medium weak_crypto / CWE-327 · 置信度 0.8 · candidate / rule_verified+llm

位置：013.php:26-27

013.php:27 执行 $pass_new = md5( $pass_new );，将用户新口令以无盐 MD5 单轮哈希后写入 users 表（013.php:30 的 UPDATE 语句）。MD5 属于已破译的快速哈希算法：存在公开碰撞构造，且 GPU 下每秒可计算数十亿次候选，配合彩虹表可对常见口令实现秒级还原。代码中未见盐值、未见迭代次数、未见 password_hash()/password_verify() 等口令专用 KDF，属于把通用摘要算法误用于口令存储的安全用途。

影响：一旦数据库（users 表 password 列）因 SQL 注入、备份泄露或越权读取而外泄，攻击者可用彩虹表/暴力破解在极短时间内还原明文口令；由于用户普遍复用口令，可进一步横向登录其他系统，造成账户接管与凭据扩散。无盐设计还使相同口令产生相同哈希，可被用于批量识别同口令账户。

CVE/CWE 论证：CWE-328（Use of Weak Hash）：MD5 用于口令这一安全用途，抗碰撞性与抗暴力破解能力均不满足口令存储要求。外部可达性：任何能提交修改密码表单的用户都会触发该哈希路径，无需额外权限。利用链闭合度：算法调用点（013.php:27）与存储点（013.php:30）在同一文件内闭合，属配置/实现型弱点，不依赖 HTTP 污点链；本条为源码语义命中，未做运行时验证。

修复建议：1) 改用 PHP 内置口令 API：$hash = password_hash($pass_new, PASSWORD_DEFAULT); 校验时用 password_verify()；2) 若需兼容旧数据，登录成功时对旧 MD5 记录做透明升级（rehash）；3) 强制口令复杂度与最小长度，禁止弱口令；4) 数据库连接使用最小权限账户，限制对 users 表的读取面，降低哈希外泄后的影响；5) 迁移期如需摘要，至少使用带盐的 PBKDF2/Argon2id 并设置足够迭代次数。
