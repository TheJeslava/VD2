F-1 037.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：037.php:11-13

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入，该值在 037.php:5 被读取后直接拼接到 SQL 语句中：037.php:11 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id' LIMIT 1;"`，`$id` 被原样嵌入单引号字符串内，未做类型转换、转义或参数化；随后 037.php:13 调用 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行该语句。由于拼接发生在 SQL 语法层，攻击者只需闭合单引号即可改变查询语义（例如 `id=1' OR '1'='1` 或 UNION 注入），校验无效的根本原因是全程没有使用 prepared statement 或 `mysqli_real_escape_string` 等任何净化手段。代码注释显示已移除 `or die` 以抑制 MySQL 错误回显，这会降低报错型注入的可见性，但不影响布尔/UNION 型注入成立。

影响：数据库查询逻辑可被任意篡改：可绕过 `user_id` 条件读取 users 表全部记录（first_name/last_name 泄露），可进一步通过 UNION 查询读取同库其他表（如用户名、口令散列等敏感数据），在数据库账户权限较高时还可能结合文件读写或堆叠语句造成更严重后果。属于未授权即可触发的数据泄露风险。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素未正确中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问 037.php 触发；利用链闭合：source（037.php:5 读取 `id`）→ 字符串拼接（037.php:11）→ 执行汇点 `mysqli_query`（037.php:13），中间无任何过滤或参数化，因此构成完整的注入链。证据等级为源码推断（llm_inferred），未做动态验证。

修复建议：改用参数化查询：`$stmt = $GLOBALS["___mysqli_ston"]->prepare("SELECT first_name, last_name FROM users WHERE user_id = ? LIMIT 1"); $stmt->bind_param('i', $id); $stmt->execute();`，并对 `id` 做整数白名单校验（如 `filter_var($id, FILTER_VALIDATE_INT)`）。若必须动态拼接，至少使用 `mysqli_real_escape_string` 并强制加引号，同时遵循最小权限原则，为应用数据库账户仅授予必要的 SELECT 权限。
