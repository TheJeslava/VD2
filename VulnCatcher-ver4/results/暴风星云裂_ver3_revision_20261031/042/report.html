F-1 042.php 基于 query 参数 id 的 SQL 注入（CWE-89）

critical sql_injection / CWE-89 · 置信度 0.78 · candidate / rule_verified+llm

位置：042.php:10-12

攻击者通过 HTTP 请求的 query 参数 `id` 提供输入（042.php:5 读取该参数），该值未经任何类型转换、转义或参数化处理，被直接拼接进 SQL 语句：042.php:11 构造 `$query = "SELECT first_name, last_name FROM users WHERE user_id = $id;"`，随后在 042.php:12 通过 `mysqli_query($GLOBALS["___mysqli_ston"], $query)` 执行。由于 `$id` 直接以字符串插值方式进入 SQL 文本，攻击者可闭合原有条件并追加任意 SQL 片段（如布尔盲注、UNION 联合查询、时间盲注）。代码中未见 `mysqli_real_escape_string`、`intval`、预处理语句或白名单校验，因此校验完全缺失。此外 042.php:12 的 `or die('<pre>' . mysqli_error(...) . '</pre>')` 会把数据库错误信息回显到响应中，为报错注入和结构探测提供了额外信息泄露通道。

影响：数据库数据泄露：攻击者可读取 users 表之外的任意表（如用户名、口令哈希、其他业务数据），并可借助 UNION 查询将任意查询结果回显到页面。错误回显进一步暴露库名、表名、列名与 SQL 结构。若数据库账户权限过高，还可能造成数据篡改或经由文件读写函数导致服务器文件读写，进而升级为 RCE。属于未授权远程可利用的严重级别缺陷。

CVE/CWE 论证：CWE-89（SQL 命令中特殊元素的不当中和）。外部可达性：注入点为 HTTP query 参数 `id`，无需认证即可访问 042.php 触发。利用链闭合：source（042.php:5 的 query `id`）→ 字符串拼接（042.php:11）→ 执行汇点 `mysqli_query`（042.php:12），中间无任何净化函数，链路完整闭合。错误信息回显（042.php:12 的 `mysqli_error`）增强了可利用性。证据等级为基于源码的推断（llm_inferred），未做动态验证。

修复建议：1) 使用预处理语句与参数绑定：`$stmt = $mysqli->prepare('SELECT first_name, last_name FROM users WHERE user_id = ?'); $stmt->bind_param('i', $id);`，从根本上消除拼接；2) 若必须使用字符串拼接，至少对 `$id` 做严格类型校验（`$id = (int)$_GET['id']` 或 `filter_var(..., FILTER_VALIDATE_INT)`）并配合 `mysqli_real_escape_string`；3) 关闭生产环境的数据库错误回显，改为记录日志并返回通用错误页，避免 `mysqli_error` 直接输出；4) 数据库连接账户遵循最小权限原则，仅授予所需表的 SELECT 权限。
